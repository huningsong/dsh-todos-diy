## P0 阻塞项（8 项）

### D-01 调度底座：自研、内置 ctx.schedule，还是混合
- 问题：原稿 P1/P2/P5 描述的是插件 apply 后自己轮询、ctx.effect 清理的调度器，但 DSH 已内置宿主级 `@deepseek-ai/dsh-schedule`（at/after/every/daily/weekly/cron，持久化、重启恢复、只补最近一次）。两者职责重叠，必须先定谁负责计时、谁负责状态。
- 为什么现在要定：底座决定数据模型是否要镜像内置任务、重启行为能否满足 S4、暂停恢复怎么实现；后改等于重写执行层。
- 选项：A 自研轻量调度——插件 apply 时启动 30 秒扫描器，nextRun 存单 JSON，启动时扫描补 missed，不依赖内置 schedule；B 纯内置——只做内置 schedule 的 UI 包装，砍掉 R4 与 S4 严格语义；C 混合——内置负责计时与重启恢复，插件自管规则、暂停态与 missed 判定，暂停用删除/重建实现。
- 推荐：✅ 已拍板：自研轻量调度（不依赖内置 ctx.schedule）。原推荐与分析保留如下，供回查。
- 原推荐：A，理由：R4 暂停、S4 严格 missed、全局任务、提前量、免打扰、snooze 都要求插件掌控"何时投递、投给谁"，内置只能 followup 创建会话且不支持 update；自研的持久化就是"JSON 原子写 + 启动扫描"，工作量可控，原稿 P1-P5 本来也是按自研写的。
- 影响：数据模型自持 nextRun/lastFiredAt，不需要 scheduleId 映射；API 需提供 start/stop/scanNow 三个入口；UI 要显示调度器健康状态；测试用假时钟覆盖跨月、跨年、休眠唤醒。
- 若不定：会在"内置够不够用"上反复，最后大概率两套都写，且暂停语义始终定不下来。

### D-02 N1"拉起 Agent 会话"的确切含义
- 问题：N1 只写"触发时拉起 Agent 会话投递首轮消息"，没定义是自动新建会话、向已有会话 follow-up，还是只发通知；也没定义"哪个会话"。
- 为什么现在要定：三种方案的成本差一个数量级：每次新建会话会持续产生 session 文件和模型 token；follow-up 需要任务绑定会话；纯通知不影响模型但弱化 Agent 卖点。它还决定 D-01 能否直接复用内置投递。
- 选项：A 自动新建独立会话——每次触发创建一个新会话并投首轮消息，任务不绑定原会话；B 向任务绑定的会话 follow-up，同时弹 GUI 浮层（默认浮层必出），未绑定会话的全局任务只发通知；C 不拉起 Agent，只发 GUI/系统通知，用户点击后再决定是否开会话。
- 推荐：✅ 已拍板：v1 不接入 Agent 会话，仅浮层 + 系统通知。原推荐与分析保留如下，供回查。
- 原推荐：B-（v1）——默认 `shell.overlay` 浮层；任务绑定会话时同时 `follow-up`，不自动新建会话；未绑定会话只走浮层/系统通知。理由：保留上下文、token 只花在真正需要时、与内置 schedule 的投递模型一致；A 会让"提醒"变成"批量制造会话"，C 则丢掉 N1 的核心差异。
- 影响：数据模型需存 targetSessionId；API 要按 session 过滤投递；UI 要展示"提醒到哪个会话"；测试要覆盖会话已删除或归档时的降级。
- 若不定：无法确定 1.0 是否需要多会话管理，内置 schedule 也无法直接接入。

### D-03 单次任务结束时间的语义
- 问题：S2 只写结束时间"用于结束节点提醒或展示任务周期"，没说结束时刻是否真的提醒；若提醒，开始与结束是否算两个 occurrence、fired 标记如何去重。
- 为什么现在要定：occurrence 模型是 R6/S3 防重复的基座。若开始和结束共用一个 fired 布尔值，结束时要么不触发、要么重复触发；若拆成两个 occurrence，任务完成判定、历史列表、重启恢复都要按 occurrence 记。
- 选项：A 仅展示——结束时间只用于进度条和列表展示，不产生提醒；B 两个独立 occurrence——开始、结束各算一次，分别有 fired 状态，去重键为 taskId+kind+plannedAt；C 一个 occurrence 两条子提醒——共享 fired 状态，结束提醒作为开始触发后的派生提醒，任一失败则整条重试。
- 推荐：✅ 已拍板：起止都提醒（startAt 提醒开始、endAt 提醒结束，各一次）。原推荐与分析保留如下，供回查。
- 原推荐：B（当 `triggerAt=both` 时）——开始、结束各算一个独立 occurrence，分别有 fired 状态；单次任务的默认 `triggerAt` 另列为待拍板项（需求-v1 暂定 `start`）。理由：语义最简单、可独立重试和审计；A 浪费 S2，C 的共享状态会让"开始已提醒、结束没提醒"无法表达。
- 影响：数据模型主键从 taskId 改为 taskId+occurrence；API 需支持按 occurrence 查询和重发；UI 历史列表要分"开始/结束"两类；测试要覆盖两端各触发一次且重启不重复。
- 若不定：S3 的 fired:true 无法落到正确粒度，单次任务会出现结束提醒丢失或重复。

### D-04 "工作日"的定义
- 问题：R1 只写"工作日"，没定义是固定周一至周五，还是按中国法定节假日与调休计算；也没定义用户能否手工指定例外日。
- 为什么现在要定：这决定规则模型是否要引入 calendar 数据源和例外日字段。若先按周一至周五上线，遇到国庆、春节会在假期提醒；若后补节假日，历史任务的规则语义会变，已触发记录也无法回溯。
- 选项：A 固定周一至周五，不看任何节假日；B 内置中国法定节假日/调休表，随插件版本更新（至少覆盖未来 12 个月），并允许单任务用 skipDates/extraWorkdays 覆盖；C 只做手动例外日，默认周一至周五，用户自己维护 skipDates 和 extraWorkdays。
- 推荐：✅ 已拍板：跟随中国法定节假日与调休（内置表，2024–2027）。原推荐与分析保留如下，供回查。
- 原推荐：C（v1）——固定周一至周五 + 手工 `skipDates`/`extraWorkdays`；B 的法定节假日表列入 v1.1 单独立项。理由：v1 引入节假日数据源等于把规则引擎变成日历数据运营，数据过期比没有更危险；A 在长假会误报，但 v1 可用 `skipDates` 兜底；C 维护成本低且不阻塞。
- 影响：数据模型增加 skipDates、extraWorkdays（v1）；calendarSource 与节假日查询留到 v1.1；UI v1 提供例外日编辑；测试覆盖跳过日与补班日。
- 若不定：R1 无法验收，"工作日"在不同用户那里会有两种理解，提醒可信度直接受损。

### D-05 每月 29/30/31 日遇到不存在日期
- 问题：R2 写"每月指定日期"，但没说 29/30/31 日遇到当月不存在该日期时怎么办；5 段 Vixie cron 本身无法表达"每月最后一天"，2 月 30 日、闰年 2 月 29 日都要有确定规则。
- 为什么现在要定：这是循环规则的核心分支，直接决定下一次触发时间；三种策略产生完全不同的提醒日期，且会影响月末账单、房租类高频场景。
- 选项：A 跳过该月——当月没有该日就不触发，下个月照常；B 收敛到当月最后一天——31 日规则在 4 月落到 30 日，2 月落到 28/29 日；C 顺延到下月 1 日——当月没有该日则下月 1 日补一次。
- 推荐：✅ 已拍板：顺延到当月最后一天（monthlyOverflow="lastDay" 默认）。原推荐与分析保留如下，供回查。
- 原推荐：A（v1 默认 `monthlyOverflow:"skip"`）——当月没有该日就不触发；B 作为可选 `lastDay` 开关放进 v1.1（默认关）。理由：与需求-v1 F2.3/AC-03 的 P0 验收一致；「每月 30 号」在 2 月不提醒符合字面语义，顺延会让用户误以为规则变了。
- 影响：数据模型存 dayOfMonth 与 overflowPolicy（默认 skip）；API 的 nextRun 要返回实际日期；UI 在规则旁提示"2 月无该日将跳过"；测试覆盖 28/29/30/31 与闰年。
- 若不定：每月任务的触发日期无法复现，测试没有唯一预期。

### D-06 错过策略与宽限期
- 问题：S4 写"错过标 missed 不补执行"，但内置 schedule 重启后会补最近一次错过的节点，两者直接冲突；原稿也没定义"多晚算错过"（宽限期）、missed 是否可见或可补发。
- 为什么现在要定：不定义宽限期，就无法判断一次触发是"准时"还是"错过"；不定义补发，用户会对"明明错过了却没提醒"投诉；它同时决定是否需要拦截内置补投递。
- 选项：A 严格——过点即 missed，永不补发、不弹窗；B 宽限（默认 5 分钟，超时标 missed 不弹，但历史里提供「补发一次」）；C 自动补发——与内置一致，恢复后自动补最近一次。
- 推荐：✅ 已拍板：5 分钟内补一次，超过标 missed 不补发。原推荐与分析保留如下，供回查。
- 原推荐：A+（v1）——`graceMinutes=5`，宽限期内补触发一次，超过即标 missed、不自动补发；「历史里手动补发」列入 v1.1（v1 不提供 `/missed`、`/redeliver`）。理由：既保留 S4 的"不打扰"，又容忍 DSH 启动慢与休眠唤醒；C 违背原稿且可能半夜补弹。
- 影响：数据模型增加 graceMinutes、missedAt、deliveryStatus；v1 API 只记录 missed（无补发接口）；UI 展示"已错过"但无补发按钮；测试覆盖 5 分钟内、5 分钟后、重启后三种路径。
- 若不定：S4 与内置行为二选一都没有依据，验收时无法判定"不补执行"是否成立。

### D-07 任务与会话的绑定关系
- 问题：原稿没有定义任务属于谁：是某个会话的附属物，还是全局任务；删除或归档会话时任务怎么办；没有会话时提醒投递到哪里。内置 schedule 强制绑定创建它的 Session，这个约束会传导到产品模型。
- 为什么现在要定：这决定存储主键、列表页的数据范围、N1 的投递目标和 D-01 的选型。若 1.0 先做会话绑定，后续要支持全局任务就得迁移全部数据。
- 选项：A 只做会话内任务——任务必须属于创建它的会话，会话删除则任务级联删除，列表只显示当前会话任务；B 全局任务为主——任务不属于任何会话，提醒只发 GUI/系统通知，需要 Agent 时再选一个"投递会话"；C 混合——任务默认全局，可绑定一个会话，会话删除时任务保留但标记"投递目标失效"。
- 推荐：✅ 已拍板：不做任务与会话绑定（随 D-02 取消会话通道）。原推荐与分析保留如下，供回查。
- 原推荐：C，理由：待办本质是全局的，但 Agent 投递又必须有会话；C 兼顾两者，且删除会话不会误删用户数据；A 会把插件做成会话附件，B 则让 N1 无法落地。
- 影响：数据模型增加 scope 与 targetSessionId；API 列表需支持全局/会话两种查询；UI 要有"投递到哪个会话"选择器与失效提示；测试覆盖删除会话后的任务存续。
- 若不定：任务归属反复，内置 schedule 的 session 绑定会逼着产品做成本不想要的形态。

### D-08 暂停/启用与循环任务的终止语义
- 问题：R4 只说启用/停用，没定义暂停的是整条规则还是仅本次；循环任务是否需要结束日期或次数上限；"完成本次"后是自动推进还是停止整条。
- 为什么现在要定：暂停语义决定调度器的删除/重建时机；结束条件决定规则模型字段；"完成"是用户每天都要点的动作，语义不清会导致循环任务被误停。
- 选项：A 只支持整条规则暂停/恢复，循环任务永久有效，没有结束日期或次数上限；B 整条规则暂停/恢复，循环任务可选结束日期或次数上限（二选一），每次 occurrence 完成后自动推进到下一次；C 只支持"跳过本次"，不支持暂停，循环任务永久有效。
- 推荐：✅ 已拍板：只有 pause/resume，不设结束日期/次数上限。原推荐与分析保留如下，供回查。
- 原推荐：A+（v1）——支持整条规则 `pause`/`resume`，循环任务 v1 永久有效（不设结束日期/次数上限）；B 的 `endDate`/`maxOccurrences` 列入 v1.1。理由：R4 的暂停是硬需求；结束条件需要新增状态机与迁移，v1 先冻结模型；C 与 R4 冲突。
- 影响：数据模型增加 enabled/status（v1）；endDate、maxOccurrences、occurrenceCount 留 v1.1；API 的 pause/resume 要同步调度器状态；UI v1 展示"已暂停"；测试覆盖暂停期间不触发、恢复后从未来节点继续。
- 若不定：R4 只能做成"删除任务"的伪暂停，用户恢复时会丢失原规则。

## P1 重要缺口（15 项）

### D-09 提醒提前量
- 问题：N3 只写"提醒内容可配置"，没写提前量；实际场景常要提前 10 分钟、提前一天，甚至一天加当天两次。
- 为什么现在要定：提前量会改变 nextRun 的计算口径，晚定要动调度核心和 occurrence 记录。
- 选项：A 只准点；B 每个任务一个提前量（0-1440 分钟，默认 0）；C 最多三档提前量（如提前 1 天/1 小时/准点），每档独立 fired，并支持未确认时的升级重复提醒。
- 推荐：B+（v1）——每任务一个提前量（0–1440 分钟，默认 0）；提前提醒使用独立 `phase="advance"` occurrence（key 后缀 `#advance`），并**取代**该 occurrence 的正点提醒，避免同一件事提醒两次；多档与升级提醒放 v1.1。理由：覆盖大多数"提前准备"需求，同时与需求-v1 F5.7 的验收一致。
- 影响：数据模型加 `notify.advanceMinutes`；API 的 nextRun 要减提前量并生成 `#advance` occurrence；UI 加数字输入与"提前 N 分钟"预览；测试覆盖提前量跨越前一天 23:00 的情况。
- 若不定：1.0 只能做准点提醒，后续加提前量要迁移全部任务时间。

### D-10 稍后提醒（snooze）
- 问题：提醒弹出时用户可能在开会，需要"稍后提醒"；原稿没有。
- 为什么现在要定：snooze 必须落持久化，不能只存在内存，否则重启后提醒丢失；它还会引入新的 occurrence 类型。
- 选项：A 不支持；B 预设 5/15/60 分钟，snooze 生成一条一次性延迟提醒并写入持久化，重启保留；C 预设加任意自定义时间。
- 推荐：B+（v1）——预设 5/15/60 分钟 + 自定义 1–1440 分钟（与需求-v1 F4.5 一致）；snooze 生成一条一次性延迟提醒并持久化，重启保留。理由：覆盖 90% 场景，自定义只多一个输入框，成本低。
- 影响：数据模型加 snoozedUntil、parentOccurrenceId；API 新建延迟提醒并取消原提醒；UI 三个按钮；测试覆盖 snooze 后重启仍按时提醒且原 occurrence 不重复。
- 若不定：用户只能手动重建任务，提醒会被误关掉。

### D-11 免打扰与静音
- 问题：夜间或周末提醒会打扰；原稿没有静音设置。
- 为什么现在要定：静音直接改变"是否投递、何时投递"，与 D-06 的 missed 判定耦合。
- 选项：A 不做；B 全局免打扰时段（默认 22:00-08:00）加周末开关，落在时段内延迟到结束时刻合并为一条摘要，超过 12 小时则标 missed；C 只做按任务设置。
- 推荐：B（默认关）——全局免打扰时段（`dnd.enabled=false` 默认关闭，用户可一键开启并设 22:00–08:00）+ 周末开关；**v1 不做任务级覆盖**（留 v1.1）。理由：默认开会在首日就静音掉早间提醒，违背"打开即用"；默认关、设置页一键开更稳妥。
- 影响：数据模型加 quietHours 与任务级覆盖；API 投递前要过静音判定；UI 设置页加时段选择；测试覆盖 21:59/22:00 边界与跨天时段。
- 若不定：夜间提醒会直接损害信任，用户可能整体关掉通知。

### D-12 多端去重与已读回执
- 问题：DSH 可能同时开多个窗口或标签页，同一提醒会弹多次；刷新后是否重复；已读、忽略状态存哪里，原稿没定义。
- 为什么现在要定：去重状态放前端还是后端，决定是否需要服务端 lastFiredAt，也决定 R6 在多端下能否成立。
- 选项：A 前端内存去重，刷新即失效；B 前端 localStorage 已读表，服务端不存；C 以插件持久化的 occurrence 状态为准（lastFiredAt 加 delivered/read 状态），多窗口用 BroadcastChannel 只做展示层去重。
- 推荐：C，理由：刷新、重启、多窗口都以同一份记录为准；B 换浏览器或清缓存后仍会重复。
- 影响：数据模型加 deliveredAt、readAt、ignoredAt；API 提供标记已读/忽略；UI 多窗口同步；测试覆盖双窗口同时在线、刷新、重启三种去重。
- 若不定：R6 只能保证单窗口，多开必重复弹。

### D-13 时区
- 问题：R5 默认 Asia/Shanghai，但没定义任务级时区、跨时区修改、DST 规则；用户出差时"09:00"指哪里的 09:00 没说。
- 为什么现在要定：时区是 nextRun 计算的一部分，存储里不存时区，后补等于全量重算。
- 选项：A 全局固定 Asia/Shanghai；B 默认 Asia/Shanghai，任务级可覆盖任意 IANA 时区，修改后未来节点按新时区重算、历史记录不改；C 跟随浏览器或系统时区。
- 推荐：B，理由：默认符合原稿，任务级覆盖解决出差和跨区；C 会让同一任务在不同设备触发时间漂移。
- 影响：数据模型加 timeZone；API 的 nextRun 需按任务时区计算；UI 显示"Asia/Shanghai (UTC+8)"并可改；测试覆盖跨时区修改与 DST 跳变（用美国时区做样例）。
- 若不定：跨时区用户会少提醒或多提醒一小时。

### D-14 通知渠道与降级顺序
- 问题：N2 只写"可选 DSH 通知"，但 DSH 没有独立系统通知服务；实际可用的是 shell.overlay 页面内浮层、浏览器 Notification（需权限）、Agent 会话消息，三者可达性不同。
- 为什么现在要定：渠道决定投递代码路径与失败重试策略，也是 N2 能否验收的标准。
- 选项：A 只用页面浮层；B 按"Agent 消息 > 系统通知 > 页面浮层"逐级降级，任务可单独选渠道；C 只用浏览器系统通知。
- 推荐：B-（v1）——`overlay` 必有 → `session` 可选 → `system` 可选（页面不可见时尝试）；任务可单独选渠道。理由：DSH 在前台时浮层必达，后台时只有系统通知有意义；单一渠道都会漏提醒。与需求-v1 F5.1–F5.3 一致。
- 影响：数据模型加 channels 数组；API 投递要返回实际渠道；UI 任务编辑加渠道勾选；测试覆盖通知权限被拒的降级路径。
- 若不定：N2 写不出验收标准，通知权限被拒时可能静默失败。

### D-15 提醒内容模板与变量
- 问题：N3 只写"内容可配置"，没定义变量、格式、是否支持 Markdown、是否带操作按钮。
- 为什么现在要定：模板渲染要在投递层实现，变量集合也会写进数据模型和文档。
- 选项：A 纯文本固定模板；B 支持 `{title}/{time}/{note}/{phase}` 变量，纯文本、禁止 HTML，操作按钮由 UI 固定提供；C 完整模板引擎或条件逻辑。
- 推荐：B-（v1）——变量集统一为 `{title}/{time}/{note}/{phase}`（与需求-v1 F5.4 一致），纯文本渲染、变量 HTML 转义、不支持 Markdown；操作按钮由 UI 固定提供。理由：覆盖个性化且不会引入注入风险；C 对提醒场景过度，还会让模板难调试。
- 影响：数据模型加 template；API 渲染时做变量转义；UI 加变量插入按钮与预览；测试覆盖变量缺失、Markdown 转义、超长内容截断。
- 若不定：N3 只能做成一句固定文案，用户无法改内容。

### D-16 提醒历史与审计
- 问题：原稿只有当前任务状态，没有历史；用户排障时最常问"昨天为什么没提醒"。
- 为什么现在要定：历史表结构要与 occurrence 模型一起设计，后补需要回填和额外迁移。
- 选项：A 不保留历史，只留最后触发时间；B 保留最近 90 天 occurrence 记录（计划时间、实际时间、状态、渠道），支持筛选与手动补发；C 永久保留并支持导出。
- 推荐：B，理由：90 天足够排障，又能控制单 JSON 体积；C 需要分页和归档，第一版成本高。
- 影响：数据模型新增 occurrence 表或数组；API 提供历史查询；UI 加"历史/已错过"页签；测试覆盖 90 天滚动清理与补发幂等。
- 若不定：错过和失败都无法解释，只能让用户重装。

### D-17 权限与安全
- 问题：插件若暴露 HTTP 路由需要鉴权；浏览器通知权限可能被拒；多人共用一台机器时任务是否互相可见，原稿都没写。
- 为什么现在要定：鉴权中间件要在路由定义前就位，后加容易漏路由；共用机器还会影响数据目录规划。
- 选项：A 无鉴权，仅限 localhost；B 所有路由走 connection.requestRejection 鉴权，通知权限被拒时降级到浮层并提示一次，任务按 DSH 用户隔离；C 只做权限提示，不做路由鉴权。
- 推荐：B，理由：路由鉴权是底线，权限降级决定提醒是否可达；A 在共用机器上会泄露任务内容。
- 影响：数据模型加 ownerId；API 统一鉴权中间件；UI 首次启动引导授权；测试覆盖未授权请求、权限拒绝、多用户隔离。
- 若不定：存在未授权读取任务内容的风险，且授权失败时用户不知道提醒为什么没弹。

### D-18 数据导入导出、迁移与 schemaVersion
- 问题：任务是单 JSON 存储，升级、换机、误删都需要备份；内置 schedule 已有任务能否导入；schema 变更怎么迁移，原稿没写。
- 为什么现在要定：schemaVersion 和迁移链必须在第一次写盘前确定，否则 1.0 发出去就无法平滑升级。
- 选项：A 不做，坏了重配；B 提供 JSON 导入导出、schemaVersion 字段、启动时顺序迁移（v1→v2），并从内置 schedule 只读导入一次性任务；C 只做导出不做导入。
- 推荐：B，理由：成本低、避免用户数据丢失；导入时按"标题+规则+时间"去重，ID 冲突一律发新 ID。
- 影响：数据模型加 schemaVersion；API 提供 export/import/preview；UI 设置页加备份按钮；测试覆盖旧版本文件导入、重复导入、损坏 JSON。
- 若不定：任何字段调整都是一次破坏性升级，用户数据只能手工修。

### D-19 是否保留内置 `schedule_*` 工具并存
- 问题：DSH 内置 `schedule_create/list/update/delete` 会与本插件的 `todo_reminder_*` 同时出现在 `standard`/`cordis`/`ptc` preset 的会话里，用户和模型都可能选错工具。
- 为什么现在要定：工具描述决定模型选哪个；若两者并存但描述不区分，模型会用内置工具创建"会话提醒"，绕过本插件的暂停/起止/例外日能力。
- 选项：A 并存，互不干扰，在工具描述里写清区别；B 在插件文档中建议用户只用本插件；C 尝试禁用内置工具（会影响其它插件的会话提醒）。
- 推荐：A + B（v1）——并存；`todo_reminder_*` 的描述首句写"管理工作待办（非会话提醒）"，并提示内置 `schedule_*` 用于会话提醒；不尝试禁用内置工具。
- 影响：工具描述需专门写；测试需覆盖"模型在两套工具间正确选择"的提示词评估；UI 帮助页说明两者区别。
- 若不定：模型会在两套工具间随机选择，导致任务进了错误的存储、无法暂停或查不到。

### D-20 优先级是「派生」还是「手工设置」
- 问题：用户提出「当天的任务优先级高、三天内中、七天内低，每天更新」。这有两种实现：派生（由截止日自动算，只读）与手工（用户自己选 P1–P4，可选自动建议）。两者数据模型与交互完全不同。
- 为什么现在要定：派生优先级不落盘、每次按当天算，实现简单且不会与用户设置冲突；手工优先级要新增 `priority` 字段、迁移与排序规则，且与「每天自动更新」天然矛盾（用户改的优先级会被次日覆盖）。
- 选项：A 纯派生（推荐）：单次按 `endAt`、循环按 `nextAt`，`priority` 只读、不落盘；B 纯手工：用户选 P1–P4，不自动变；C 混合：默认派生，允许用户锁定某条任务的手工优先级（`priorityOverride`）。
- 推荐：✅ 已拍板：纯派生优先级（单次 `endAt` / 循环 `nextAt` 为唯一时间来源，只读、不落盘；手工强调用置顶表达）。
- 原推荐：**A**。规则简单、可解释、零迁移；需要手工强调时用「置顶」表达（见 D-21），语义不重叠。
- 影响：数据模型无需 `priority` 持久字段；API 返回 `priority` 派生对象；UI 只显示不能编辑；测试用 fake clock 覆盖 24h/72h/168h ±1ms 边界。
- 若不定：会出现「用户改了优先级、第二天又被自动改回去」的矛盾体验，或规则写进数据库后无法调整阈值。

### D-21 置顶的语义与边界
- 问题：用户提出「任务置顶，完成后自动取消置顶」。需要明确：置顶是否跨分组（超期任务置顶后放哪）、置顶是否有上限、恢复为待办后是否恢复置顶、置顶是否影响提醒。
- 为什么现在要定：置顶影响排序与「已完成」的写入逻辑（完成时要原子清 pinned），也决定列表分组与超期页签的交互。
- 选项：A 单布尔 `pinned`，置顶组永远在最上方（含超期），无数量上限，完成后清空且不恢复；B 置顶只对未超期生效，超期后自动取消置顶；C 置顶带顺序号，可拖动排序。
- 推荐：✅ 已拍板：超期仍置顶（置顶组永远最上方，带「超期」红标，不沉底）。
- 原推荐：**A**。最简单且符合「最要紧的事永远在最上面」；B 会让超期任务突然沉底，正好与用户预期相反；C 增加拖拽与顺序持久化成本，放 v1.1。
- 影响：`pinned:boolean` + 完成时原子写；排序 `pinned → priority → endAt/nextAt`；UI 淡琥珀底 + 📌；测试覆盖「置顶+超期」「完成清置顶」「恢复不恢复置顶」。
- 若不定：用户会看到置顶任务在超期后突然消失到列表下方，或完成后又在「已完成」里显示置顶标记。

### D-22 任务视图与暂停口径（D-25 已扩展）
- 问题：任务列表按什么阶段分页？暂停任务归到哪里？已完成保留多久？超期是否包含暂停任务？
- 为什么现在要定：口径决定 API 的 `view` 参数、计数徽标、阶段派生与归档策略。
- 选项：A（D-25 采纳）四个阶段页签「未开始 / 进行中 / 已超期 / 已完成」只覆盖单次任务；循环任务独立 `recurring` 筛选；`paused` 独立筛选/折叠区，不混入任何阶段页签；B 三份独立列表；C 超期单独存储为派生副本（不采纳）。
- 推荐：✅ 已拍板：未开始/进行中/已超期只对单次任务生效；循环任务单列；暂停 = 主动搁置，不算超期、不参与优先级、独立筛选。
- 影响：API `/snapshot?view=notStarted|inProgress|overdue|done|recurring|paused`；`counts` 六项；暂停任务不计入四阶段徽标；测试覆盖「暂停的超期任务」「循环任务筛选」。
- 若不定：暂停任务会被塞进阶段页签，徽标数与行数不一致；循环任务会被误算成进行中。

### D-24 「已完成」保留策略与季度归档
- 问题：用户要求「已完成持久化长期保存本地，每季度生成一个历史文件」，但没有定义：主文件是否还保留已完成任务、归档按什么时间切、归档后如何查询/恢复、崩溃一致性怎么保证。
- 为什么现在要定：这决定主文件体积增长、`/snapshot?view=done` 的查询范围与归档目录结构；后改需要迁移所有已完成记录。
- 选项：A（推荐）主文件只保留本季度 `done` 任务；每季度首个 tick（1/4/7/10-01 00:00 之后）把上一季度已完成任务移入 `archive/completed-YYYY-Qn.json`，`archive/index.json` 建索引；归档永久保留、可查询、可恢复；B 主文件保留全部已完成任务、不归档（简单但文件会一直增长）；C 按年归档（文件更少但粒度粗）。
- 推荐：**A**。季度粒度符合「季度总结」的管理习惯，单文件增长可控（每季度约几十到几百条），且归档文件仍是纯 JSON，可直接备份/检索。B 在 3–5 年后主文件会到数 MB、每次全量重写变慢；C 粒度太粗，跨季度查询不便。
- 影响：新增 `archive/` 目录、`archivedQuarter` 字段、`/archive` 与 `/archive/index` 接口、`archiveCompleted()` 季度任务；「已完成」页签增加「本季度 / 历史归档」切换；测试覆盖跨季度、崩溃对账、归档恢复、归档损坏。
- 若不定：主文件无限增长，或归档后历史任务查不到/恢复不了。
