# 自然语言录入任务 — 可行性评估（D-25 前历史稿）

> 日期：2026-10-30 ｜ 评估对象：候选特性「用户输入一句话 → 自动填任务表单 → 用户补缺失项」
> **状态：历史评估稿。** 文中 `dueDate`、三视图、`startAt` 必填/默认 09:00 等字段已随 D-25/v1.3 变更；NLP 仍为 v1.1 候选，实施前必须按 `需求-v1.md` v1.3 重写。
> 结论：**技术可行，整体难度中等**。建议放在 v1.1，不阻塞 v1.0 上架；MVP 约 4–6 人日，完整质量约 7–10 人日。

---

## 1. 需求理解

用户在一个输入框里输入自然语言，例如：

> 每周五下午 5 点提醒我交周报，提前 10 分钟

系统应当：

1. 识别出这是一条**循环任务**（weekly / 周五 / 17:00 / 提前 10 分钟）；
2. 把能确定的字段填入现有「新建任务」表单；
3. 把没说的必填项留空并**高亮提示用户补充**（例如单次任务的结束时间）；
4. 用户确认/补充后，仍走现有 `POST /tasks/create` 保存。

关键原则：**只预填、不自动创建**。用户始终看到并确认最终表单。

---

## 2. 结论摘要

| 维度 | 评价 |
|---|---|
| 技术可行性 | **高**。DSH 0.2.1-rc.3 宿主已提供 `ctx.llm`（provider-neutral 模型流式服务）与 `ctx.agentDefaultModel`（默认模型选择），插件不需要引入任何 `@deepseek-ai/*` 运行时依赖 |
| 工程难度 | **中等偏低（2.5/5）**。新增一个宿主 `/parse` 路由、一个客户端快速输入组件、编辑器缺失字段标记；现有 `TaskDraft`、`draftToPayload`、宿主校验、下次触发预览都可直接复用 |
| 产品难度 | **中等偏高（3.5/5）**。难在中文歧义、缺失字段策略、插件能力边界，不在代码量 |
| 工作量 | **MVP 4–6 人日**；完整质量（100 条语料 + 边界 + 文档）**7–10 人日** |
| 主要风险 | 模型不可用、隐私（任务文本发给模型）、解析结果“合法但理解错”。均可通过「永不自动保存 + 失败回退空表单 + 表单预览」兜底 |
| 建议 | **v1.1 做**，入口放任务列表上方；v1.0 先上架 |

一句话：**代码不难，难在“猜得准”和“猜错时用户能一眼发现”。**

## 3. 现有基础（为什么这件事比想象中容易）

| 已有能力 | 位置 | 对本特性的价值 |
|---|---|---|
| `TaskDraft` 草稿模型 | `src/client/task-editor.ts` | 解析器只需要产出一个 `Partial<TaskDraft>`，不用碰数据库 |
| `draftToPayload()` | 同上 | 草稿 → API 请求的转换已存在 |
| 宿主 `validateCreate` | `src/host/validate.ts` | 兜底校验，模型给错值也不会写坏数据 |
| 编辑器「未来 5 次触发」预览 | `TaskEditor` 内 `preview` | 用户保存前可直接看出“周五 17:00”理解对不对 |
| 空表单默认值 | `emptyDraft()` | 缺失字段有合理默认（09:00、工作日、Asia/Shanghai） |
| `ctx.llm.stream()` | 本机 DSH `@deepseek-ai/dsh-llm` | 直接调用用户已配置的模型，无需自建模型客户端 |
| `ctx.agentDefaultModel.currentSelection()` | 本机 DSH `@deepseek-ai/dsh-agent-default-model` | 拿到默认 provider/model，用户无需额外配置 |
| Agent 工具 `todo_reminder_create` | `src/host/toolDefs.ts` | **对话式自然语言录入已经可用**（用户在会话里说，Agent 调工具建任务），本特性只是把它搬进面板表单 |

> 补充：DSH 内置的「自动化任务」页面自己也没有自然语言表单，它的做法是点「新建」→ 打开一个新会话 → 由模型在该会话里创建任务（见 `dsh-client-ui-schedule` 的 README）。这说明 DSH 官方也认为“中文自然语言 → 结构化任务”适合交给模型，而不是手写解析器。

## 4. 方案对比

| 方案 | 做法 | 准确率 | 工作量 | 结论 |
|---|---|---|---|---|
| A. 纯本地规则解析 | 自己写中文日期/时间/重复规则语法 | 70–85%（长尾很差） | 8–12 人日 | 不推荐。中文表达长尾太长，标题切分几乎做不好 |
| B. 模型解析（推荐） | `ctx.llm` 输出 JSON → 校验 → 填表单 | 90–95%（配好 prompt） | 4–6 人日 | **推荐**。复用 DSH 模型能力，零新增运行时依赖 |
| C. 混合 | 本地规则先解析常见句式，失败再调模型 | 92–96% | 7–9 人日 | 过度设计。两套解析器 = 两套测试与维护 |
| D. 对话式（已有） | 用户在会话里说，Agent 调 `todo_reminder_create` | 95%+ | 0 | 已可用，但不在面板表单里，且会产生会话消息（D-02 不介入） |

第三方库（`chrono-node-zh`、`time_parser` 等）只能解决“日期时间”这一小块，解决不了“标题是什么、是循环还是一次性、缺什么字段”，且会引入依赖与长期维护成本。不建议作为主方案。

## 5. 推荐方案

### 5.0 先澄清：`ctx.llm` 不是「接入会话」，也不是「插件直接调 API」

三条路径要分开看：

| 路径 | 做法 | 是否产生会话 | 插件是否管 API Key | 结论 |
|---|---|---|---|---|
| A. Agent 会话 | 打开/恢复一个会话，让 Agent 调 `todo_reminder_create` | **是**，有聊天记录与模型轮次 | 否 | D-02 已排除；面板表单不走这条 |
| **B. 宿主 `ctx.llm` 服务（推荐）** | 插件宿主进程内调用 `ctx.llm.stream()`，DSH 路由到已配置的 provider adapter | **否**，没有会话/聊天记录/tool call | **否**，凭据在 DSH 配置里 | **推荐** |
| C. 插件直接 HTTP 调 DeepSeek API | 插件自己 `fetch`、自己读 `DEEPSEEK_API_KEY`、自己处理流式/重试/错误 | 否 | **是**，还要管理 baseURL、密钥、超时 | 不推荐，重复造轮子且有密钥泄露风险 |

`ctx.llm` 的实际调用链：

```text
插件 host（parse 路由）
  └─ ctx.llm.stream({ provider, model, messages })
       └─ DSH LlmRuntime（宿主服务，负责路由/校验/流式/错误码）
            └─ provider adapter（dsh-llm-deepseek 或 dsh-llm-pi-ai）
                 └─ HTTPS → DeepSeek 官方 API / Magpie 网关 / 其他已配置提供方
```

所以：

- **不需要接入 DeepSeek 的会话**：`ctx.llm` 不经过 `sessionController`，不创建会话、不产生聊天记录、不触发 Agent loop，也不出现在会话列表里。
- **也不是插件直接调 API**：插件只调用 DSH 的宿主服务，API Key、baseURL、重试、流式解析都由 DSH 的 provider adapter 负责。插件产物仍然零 `@deepseek-ai/*` 运行时依赖。
- **用哪个模型由 DSH 配置决定**：默认取 `ctx.agentDefaultModel.currentSelection()`；这台机器当前是 `magpie / workbuddy-deepseek-v4.1-flash`，实际请求发往 Magpie 网关，而不是插件里写死 DeepSeek 官方地址。
- **费用**：模型调用会消耗当前配置的提供方额度（本机是 Magpie 网关），但一次解析只有几百 token，成本可忽略。

### 5.1 架构

```text
┌─────────────────────────────────────────────────────────────┐
│ 客户端 Panel                                                 │
│  [✨ 自然语言新建] 输入框：每周五下午5点提醒我交周报，提前10分钟  │
│         │ Enter / 点击「解析」                                │
│         ▼                                                    │
│  POST /api/dsh-todos-diy/parse  { text, timeZone }           │
└─────────┬───────────────────────────────────────────────────┘
          │
┌─────────▼───────────────────────────────────────────────────┐
│ 宿主 parse 路由（新增 src/host/parse.ts）                     │
│  1. ctx.agentDefaultModel.currentSelection() → provider/model │
│  2. ctx.llm.stream({ provider, model, messages, signal })     │
│  3. 收集文本 → 提取 JSON → zod/手写校验 → 规范化               │
│  4. 返回 { draft, missing, unsupported, confidence }          │
│  失败（无模型/超时/JSON 坏）→ 返回 degraded=true              │
└─────────┬───────────────────────────────────────────────────┘
          │
┌─────────▼───────────────────────────────────────────────────┐
│ 客户端 TaskEditor（复用现有弹窗）                              │
│  · 已识别字段：正常显示                                       │
│  · 默认值字段：灰字「默认」                                    │
│  · 缺失必填：黄色圆点 + 顶部「还需补充：结束时间」               │
│  · 未来 5 次触发预览（已有）                                   │
│  · 用户点「保存」才写库                                        │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 交互流程

1. 任务列表顶部（搜索框旁）增加一个 `✨` 按钮；点击展开单行输入框。
2. 用户输入一句话，按 Enter 或点「解析」。
3. 按钮进入 loading（≤ 8 秒超时）。
4. 解析成功后直接打开现有 `TaskEditor`：
   - 顶部横幅：「已按你的描述填入 6 项，还需要补充：结束时间」；
   - 缺失字段标黄，自动聚焦第一个缺失项；
   - 底部仍显示「接下来 5 次」预览；
   - 所有字段可改。
5. 用户点「保存」→ 走 `POST /tasks/create`；失败仍显示现有错误码。
6. 解析失败/模型不可用：打开同一个编辑器，`title` 填入原文（截断 200 字），其余为空，toast「自动解析不可用，已保留原文，请手动补充」。
7. 用户关闭编辑器 → 不留下任何任务，输入框保留原文（仅内存，不持久化）。

### 5.3 返回结构（建议）

```json
{
  "draft": {
    "kind": "recurring",
    "title": "交周报",
    "description": "",
    "dueDate": null,
    "preset": "weekly",
    "time": "17:00",
    "weekdays": [5],
    "monthDays": [],
    "cron": "0 17 * * 5",
    "holidayCalendar": "CN",
    "monthlyOverflow": "lastDay",
    "skipDates": [],
    "extraWorkdays": [],
    "channels": ["overlay"],
    "advanceMinutes": 10,
    "sound": false,
    "template": "{title}｜{time}\n{note}"
  },
  "fieldStatus": {
    "title": "explicit",
    "kind": "explicit",
    "time": "explicit",
    "weekdays": "explicit",
    "advanceMinutes": "explicit",
    "description": "missing"
  },
  "missingRequired": [],
  "unsupported": [],
  "confidence": 0.93
}
```

- `fieldStatus` 三态：`explicit`（用户明确说了）/ `default`（系统默认值）/ `missing`（没说且无合理默认）。
- `missingRequired` 只列**必填且缺失**的字段，用于顶部提示与聚焦。
- `unsupported` 用于能力边界外的表达（见 §7）。

## 6. 字段映射与缺失策略

| 用户说法 | 映射字段 | 缺失/未说时 |
|---|---|---|
| 「交周报」「提醒我开会」 | `title` | 取原文去掉时间/提醒词后的核心短语；无法切分时用原文（≤200 字） |
| 「每周」「每天」「每月」「工作日」 | `kind=recurring` + `preset` | 只有一个具体日期 → `kind=once` |
| 「明天 9 点」 | `once.startAt` | 只有日期没时间 → 09:00（标记 `default`） |
| 「到 11 点」「9 点到 11 点」 | `once.endAt` | 未说结束 → start + 1 小时（标记 `default`，用户可改） |
| 「下午 3 点半」 | `time` / `startAt` | 未说上下午 → 按 24 小时制字面值，标记低置信 |
| 「每周一三五」 | `weekdays=[1,3,5]` | 只说「每周」→ `missing`，必须补 |
| 「每月 15 号」「月底」 | `monthDays=[15]` / `[31]` + `monthlyOverflow=lastDay` | 只说「每月」→ `missing` |
| 「周五前必须交」「截止周五」 | `dueDate=2026-10-30`（只对一次性任务） | 未说 → `null`（无截止）；循环任务默认不设 |
| 「提前 10 分钟」 | `advanceMinutes=10` | 未说 → 0 |
| 「提醒我」 | 无字段 | — |
| 未提到的渠道/声音/模板 | `channels=["overlay"]`、`sound=false`、默认模板 | 用默认值 |

**为什么结束时间默认 +1 小时而不是强制留空**：D-03 要求单次任务必须有起止两个提醒点，但用户口语里经常只说开始。强制留空会让每次创建多一步；+1 小时是可编辑的合理估计，并在表单上标「默认」。如果用户要精确，一眼就能改。

**关于 `dueDate`**：它和提醒时间完全分离——只用于优先级、超期页与排序，不产生提醒。自然语言解析只在用户明确说「前/截止/到期」时填写；否则留空（`无截止`）。循环任务尤其不要自动填 `dueDate`：当前模型里它是任务级固定日期，不会随每次 occurrence 滚动，填了以后一旦过了那天会一直显示超期（这是现有实现的一个待决策点，见 §12 的 NL-08）。

## 7. 难点拆解

| 难点 | 难度 | 说明 | 对策 |
|---|---|---|---|
| 中文时间表达 | 中高 | 「下周一」vs「这周一」「月底」「周五前」「隔周」「差一刻十点」「上午/下午」 | 把「今天日期 + 星期 + 时区」放进 prompt；模型输出本地 `YYYY-MM-DDTHH:mm`；宿主再校验日期合法、不在过去 |
| 任务类型判定 | 中 | 「每周五交周报」是循环，「这周五交周报」是一次性；中文常省略主语 | prompt 给判定规则 + few-shot；表单顶部显示 `kind` 可一键切换 |
| 标题/描述切分 | 中 | 「提醒我周五下午三点交季度总结」要得到「交季度总结」 | 模型擅长；再加规则：去掉「提醒我/记得/别忘了」等前缀，长度 ≤ 200 |
| 能力边界 | 中 | 模型可能解析出插件不支持的规则：每 N 天、每 N 小时、每月最后一个工作日、农历生日、第 N 个星期几 | 维护「支持矩阵」；prompt 明确禁止；返回 `unsupported`，UI 提示「暂不支持，已按最接近的规则填入，请检查」 |
| 缺失字段策略 | 中 | 哪些必填、哪些给默认、哪些必须问 | 用 `fieldStatus` 三态 + `missingRequired`；顶部横幅列出待补项 |
| 歧义/多任务 | 中 | 「明天 9 点开会，后天 10 点交材料」一句话两件事 | v1.1 只解析第一个任务；检测到多个时间点时提示「一次只能解析一个任务，请分开输入」 |
| 模型可用性 | 中 | 用户可能没配 provider、额度用完、网络失败、8 秒超时 | 路由先探测 `ctx.llm` / `agentDefaultModel`；失败回退到普通新建表单，原文进 title |
| 隐私 | 中 | 任务文本会发给模型提供方，而插件一直承诺“数据只存本地” | 首次使用弹一次说明；设置项可关闭；关闭后不显示 `✨` 入口 |
| 可解释性 | 中 | 用户不知道哪些是“猜的” | 三态标记 + 原始描述折叠展示 + 未来 5 次预览 |

## 8. 工作量估算

| 工作项 | 人日 | 说明 |
|---|---|---|
| 宿主 `/parse` 路由 + 模型调用 + 默认模型解析 + 超时/降级 | 2.0 | `ctx.llm.stream`、`ctx.agentDefaultModel`、错误码映射 |
| Prompt + JSON schema + 结果校验/规范化 | 1.0 | 含 cron 规范化、时间补全、过去日期检查 |
| 客户端快速输入框 + 编辑器字段状态/缺失提示 | 1.5 | 复用现有 `TaskEditor`，新增 `fieldStatus` 渲染 |
| 测试：mock 模型 + 80–120 条中文语料 + 边界 | 1.5 | 字段级断言；模型不可用/坏 JSON/超时 |
| i18n、README、设置项、发布 | 0.5 | 中英双语文案 |
| **合计** | **6.5 人日**（范围 4–8） | 不含多任务、语音 |

对比：如果只做「输入框 + 模型解析 + 普通表单预填」不做字段状态高亮，约 **3 人日**，但用户很难发现“猜错了”，不建议省这 1–2 天。

## 9. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 模型把「下周一」算错 | 中 | 提醒错日 | 表单显示完整日期+星期+未来 5 次预览；保存前必须用户确认 |
| 模型返回非法 JSON/字段 | 中 | 解析失败 | 严格 schema 校验；失败重试 1 次；仍失败回退原文表单 |
| 模型服务不可用 | 中 | 功能不可用 | 按钮置灰/隐藏；普通新建不受影响 |
| 任务文本泄露给模型提供方 | 低–中 | 隐私 | 首次说明 + 可关闭；不持久化原始输入 |
| 用户期望“一句话直接建好” | 高 | 多一步确认被嫌烦 | 明确产品定位是“预填 + 补充”，不是“自动创建”；保存只需一次点击 |
| 解析结果“合法但语义错” | 中 | 用户存错任务 | 三态标记 + 预览 + 不做自动保存；这是本方案最重要的安全阀 |
| 客户端 bundle 变大 | 低 | 首屏变慢 | 解析逻辑全在宿主；客户端只加一个输入框和状态渲染（<10KB） |

## 10. 验收标准建议（若纳入需求）

| 编号 | 验收 |
|---|---|
| F10.1 | 任务列表顶部提供「自然语言新建」入口；点击展开单行输入框，Enter 或按钮触发解析 |
| F10.2 | 解析结果必须填入现有 `TaskEditor`，不得跳过表单直接创建 |
| F10.3 | 每个字段标注来源：`explicit` / `default` / `missing`；缺失必填项在顶部汇总并聚焦 |
| F10.4 | 单次任务缺结束时间时默认 +1 小时，并标记为默认值，可修改 |
| F10.5 | 模型不可用 / 超时（8 秒）/ 非法 JSON 时，回退为普通新建表单，原文填入 title，不丢用户输入 |
| F10.6 | 原始输入仅保存在客户端内存，关闭编辑器即丢弃；不写入 `tasks.json`、不写日志 |
| F10.7 | 首次使用展示模型调用说明；设置项可关闭该功能，关闭后入口隐藏 |
| F10.8 | 能力边界外表达（每 N 天/每 N 小时/每月最后一个工作日/农历）给出明确提示，不静默降级 |
| F10.9 | 中英文界面文案完整；无硬编码中文 |
| AC-40 | 输入「每周五下午5点提醒我交周报，提前10分钟」→ 表单为 recurring/weekly/周五/17:00/提前10分钟，保存后下次触发正确 |

## 11. 范围建议

**v1.1 做（MVP）**
- 单任务、中文为主（英文顺带支持）
- 循环/单次两类，覆盖 workdays/weekly/monthly/custom
- 预填 + 三态 + 缺失提示 + 回退
- 模型不可用降级

**以后再做**
- 一句话多个任务（拆成多张草稿）
- 语音输入（DSH 已有 experimental speech-to-text，可后续接）
- 从用户修改中学习（记住“我习惯提前 10 分钟”）
- 本地规则引擎（只在完全离线场景需要）

**不做**
- 自动创建不确认
- 自建模型客户端/API Key 管理（直接用 `ctx.llm`）
- 本地 NLP 训练

## 附录 A：Prompt 草案

```text
你是「工作待办」插件的任务解析器。把用户的一句话解析成 JSON，只输出 JSON，不要 Markdown。

当前时间：{now}（{timeZone}，{weekday}）
默认时区：{timeZone}

规则：
- kind: "once" 或 "recurring"
- once: startAt/endAt 用本地时间 "YYYY-MM-DDTHH:mm"，endAt 必须晚于 startAt
- recurring: preset 取 "workdays" | "weekly" | "monthly" | "custom"
  - workdays: time "HH:mm"，holidayCalendar "CN"（默认）或 "none"
  - weekly: time + weekdays [1..7]（周一=1）
  - monthly: time + monthDays [1..31]，monthlyOverflow "lastDay"（默认）
  - custom: cron 五字段
- notify.advanceMinutes: 0–1440 的整数，未说填 0
- title: 去掉「提醒我/记得/别忘了」后的核心短语，≤200 字
- 用户没明确说的字段一律填 null，不要猜；不要编造日期
- 不支持的表达（每N天、每N小时、每月最后一个工作日、农历、第N个星期几）放进 unsupported

输出 JSON：
{
  "kind": "once|recurring|null",
  "title": "string|null",
  "description": "string|null",
  "dueDate": "YYYY-MM-DD|null",
  "once": {"startAt":"...","endAt":"..."}|null,
  "rule": {"preset":"...","time":"HH:mm","weekdays":[...],"monthDays":[...],"cron":"...","holidayCalendar":"CN","monthlyOverflow":"lastDay"}|null,
  "notify": {"advanceMinutes":0}|null,
  "missing": ["..."],
  "unsupported": ["..."],
  "confidence": 0.0
}
```
