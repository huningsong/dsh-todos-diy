# 任务时间与状态模型 — 剩余逻辑问题评估

> 日期：2026-10-30 ｜ 评估对象：需求 v1.2 / D-25 之后的任务时间与状态模型
> 注：2026-10-30 Q1 拍板后，任务侧字段已改名 `stage`；occurrence 的 `phase` 保留。下文旧称 `phase` 的位置按 `stage` 理解。
> 结论：D-25 解决了「dueDate 与 endAt 谁优先」的主冲突，但仍留下 **3 个 P0 级逻辑问题** 和 **5 个 P1 级边界问题**。P0 不解决，代码实现后会出现「循环任务永远进行中」「会议类任务结束后永远超期」「暂停任务混在进行中」等反直觉行为。

> **2026-10-30 用户拍板**：
> 1. 全部按**任务型**处理，不引入事件自动结束；会议类任务只提醒开始（`notify.endReminder=false`），开完会由用户手动完成；会议结束后未完成 → 已超期。
> 2. 循环任务使用独立阶段 `recurring`（循环中/待触发），`未开始/进行中/已超期` 只对单次任务生效，统计单列“循环任务 N”。
> 3. `已暂停` 使用独立筛选/折叠区，不混入任何阶段页签。
> 4. 边界问题按本文件建议处理（`now > endAt` 才超期；只选日期默认 23:59:59.999；`serverTime`/`nextTransitionAt`；归档迁移等）。
> 本文件保留为当时的评估记录，具体需求以 `需求-v1.md` v1.2 为准。

## 2. 三个 P0 问题详解

### 2.1 `endAt` 的「事件结束」与「任务截止」是两种语义

D-25 把 `endAt` 定为唯一截止时间，解决了 dueDate 冲突，但没有解决**任务类型**：

- **任务型**：提交材料，周五 18:00 前完成；过了 18:00 未完成 → 已超期，必须手动完成；
- **事件型**：14:00–18:00 开会；18:00 会议结束，任务应当自动结束，不应该变成“超期”。

当前模型只有一种 `endAt` 语义，二者必有一个体验是错的：
- 若按任务型：所有会议提醒都会在结束后变成超期；
- 若按事件型：所有材料任务都不会超期，D-25 的「已超期」失去意义。

**建议**：增加 `completionMode`（或 `taskType`）：

```ts
type CompletionMode = 'manual' | 'autoAtEnd'
```

- `manual`（默认，任务型）：`endAt` 是截止时间，过点未完成 → `phase='overdue'`，必须手动完成；
- `autoAtEnd`（事件型）：`endAt` 到点自动 `done`（或进入 `ended`），不进超期；
- UI 新建时用两个入口/开关：「任务（有截止）」/「事件（到点结束）」；自然语言解析按“会议/评审/通话”等关键词推断，仍可在表单切换。

如果不想引入模式，另一种简化是：**所有任务都按任务型处理，事件结束后也留在列表里等用户点完成**。但这会让日常会议堆积成超期，必须明确接受。

### 2.2 循环任务的阶段语义

当前 F4.10 把 `kind=recurring` 的所有 active 任务归为「进行中」：

- 每周五交周报：周一到周四都「进行中」；
- 每月 1 号交报表：整个月都「进行中」；
- 统计 `counts.inProgress` 包含所有循环任务，用户看到的“进行中 12 条”里可能 10 条是循环任务。

这不符合「未开始 / 进行中 / 已超期」的时间语义。循环任务本质是**长期规则**，不是一条有开始/结束的任务。

**建议**：循环任务使用独立阶段（展示名可为「循环中 / 待触发」）：

```text
phase=recurring（active 循环任务）
nextAt=下次触发时间
```

- 未开始/进行中/已超期 只对单次任务；
- 统计单独给出 `recurring` 数量，并保留 `byKind`；
- 如果要表达“每周五 09:00–17:00”这种窗口，给 rule 增加可选 `durationMinutes`；否则 `rule.time` 是点事件，不产生「进行中」窗口；
- 若要表达“本期已完成/本期已错过”，用 `state.completedOccurrenceKey` / `missedCount` 计算 `lastOccurrenceStatus`，不要塞进 `phase`。

### 2.3 暂停任务的归属

D-22 说“暂停 = 主动搁置，不算超期，不参与优先级”，但 F4.10/F8.11 又把 paused 放进「进行中」页签末尾：

- 页签徽标「进行中 N」不含 paused，但页签内实际行数包含 paused；
- 用户点「进行中」看到暂停任务，会误以为它处于活跃状态；
- 暂停任务如果原本是「未开始」或「已超期」，放进「进行中」更不准确。

**建议**：二选一

1. 增加第 5 个「已暂停」页签（最简单、最准确）；
2. 保留 4 个页签，但把「已暂停」做成全局筛选器/折叠区，不塞进任何一个阶段页签；徽标只统计当前阶段。

推荐 **方案 1**，因为用户已经要求统计每类数量，第 5 个页签正好承载「已暂停 N」。

## 3. P1 问题详解

### 3.1 默认开始时间的认知成本

用户要求“不填开始时间默认为任务创建时间”，这本身没错，但会导致：

- 创建一条未来任务（比如下周五截止），从创建那一刻起就显示「进行中」；
- 「未开始」页签只对**显式填写未来 startAt** 的任务生效，快速创建的任务永远不会出现在那里；
- 用户可能把「进行中」理解成“我正在做”，而不是“系统允许开始做”。

**建议**：保留默认创建时间，但在表单里明确提示「不填开始时间 = 创建即开始」，并在任务详情显示 `开始时间` 来源（创建时间/手动设置）；如果用户希望「未开始」，必须显式设置未来开始时间。不要把默认开始时间偷偷改成别的值。

### 3.2 循环任务的优先级与“本期错过”

`priority` 对循环任务按 `nextAt` 计算：

- 周五 17:00 的周报，周五 17:00 前 high；17:00 一过 `nextAt` 变成下周五，priority 立刻掉到 low；
- 如果用户没交，任务行没有任何“本期未完成”标记；
- `missedCount` 只在 `missed` 时增加，但正常触发后未完成不算 missed，也不进入任何状态。

**建议**：
- 循环任务不使用 once 的 `overdue` 语义；展示「上次触发：已触发/已错过/已完成」；
- 行上显示 `上次未完成` 标签（由 `lastFiredAt`、`completedOccurrenceKey`、`missedCount` 推导）；
- `priority` 对循环任务只用于“下次触发临近度”，不要把它当作任务紧急度。

### 3.3 统计口径

当前 `counts` 的 `done` 只反映主文件（本季度）已完成；历史归档的 done 不在 counts 里。`byKind` 又是全部非归档任务。用户问“每类任务数量”时可能会把两者相加，得到不一致结果。

**建议**：明确三个口径并在 UI 标注：

```json
{
  "counts": {
    "notStarted": 3,
    "inProgress": 2,
    "overdue": 1,
    "doneThisQuarter": 4,
    "paused": 1,
    "recurring": 3
  },
  "byKind": { "once": 11, "recurring": 3 },
  "totalDone": 37
}
```

- `doneThisQuarter` = 当前「已完成」页签数量；
- `totalDone` = 含历史归档的全部已完成数；
- `byKind` 是全部非归档任务，不是页签数量。

### 3.4 客户端时钟与边界刷新

F4.13 让客户端在「最近未来边界」刷新，但如果客户端用本地 `Date.now()`：

- DSH Web 从另一台机器访问时，客户端时钟可能比宿主快/慢；
- 任务在宿主 16:00 进入进行中，客户端可能 15:58 或 16:02 才刷新；
- 这不是“状态算错”，而是“显示延迟/提前”，但用户会当成 bug。

**建议**：`GET /snapshot` 返回 `serverTime`（UTC ISO）和 `nextTransitionAt`（服务端算好的最近边界）；客户端用 `serverTime` 计算偏移，按服务端时间排程，不直接信本地时钟。

### 3.5 编辑/复制/恢复的 startAt 语义

`startAt` 从“必填”改成“可选”后，以下路径必须定义：

- **编辑只改 endAt**：保留原 `startAt` 和 `startAtSource`，不要重新取当前时间；
- **显式修改 startAt**：`startAtSource="explicit"`，并重置 `firedStart`/`firedStartAdvance`/`missedStart`，否则新的开始节点可能不触发；
- **复制任务**：复制规则/窗口还是重置开始时间？建议复制时保留原 `startAt`（用户明确复制），但在 UI 提示“开始时间已复制，如需重新开始请修改”；
- **恢复归档**：恢复为 active 时保留原 `startAt`；如果已过 `endAt`，恢复后直接 `overdue`，需要提示。

## 5. 建议的最小修复顺序（若 v1.0 前只做 P0）

1. **先拍板任务类型/完成模式**（问题 1）：决定 `event` 自动结束还是所有任务手动完成；
2. **循环任务独立阶段**（问题 2）：`phase=recurring`，统计单列，`未开始/进行中/已超期`只对单次任务；
3. **暂停独立**（问题 3）：加「已暂停」页签或全局筛选；
4. 再补 P1：`serverTime`/`nextTransitionAt`、`startAt` 编辑语义、循环本期状态、统计口径；
5. P2 可在 v1.1 做。

**预计额外工作量**：P0 约 1.5–2.5 人日；P0+P1 约 3–4 人日；P2 约 1–2 人日。
