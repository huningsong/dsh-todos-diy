## 1 背景与目标

### 1.1 背景

综合管理岗位每天要处理大量**按固定节奏重复出现**的事务性提醒，以及少量**有明确起止时间**的一次性任务。现有做法依赖个人记忆、日历或聊天工具置顶，存在三个问题：

1. 规则型提醒（工作日、每周几、每月某日）散落在不同工具里，无法统一启停和查看；
2. 一次性任务的「开始」和「结束」是两个不同语义的节点，普通日历只能提醒开始；
3. 提醒工具与日常使用的 DSH 分离，切走应用就看不到，且重启后容易重复提醒或丢失状态。

DSH 已具备插件体系、宿主常驻进程、Agent 会话、本地存储与 Web GUI，适合把「工作待办提醒」做成一个随 DSH 启动、在界面内可见、可被 Agent 读写的插件。

### 1.2 目标（可验收表述）

| 编号 | 目标 | 可验收表述 |
|---|---|---|
| G1 | 打开即用 | 在 DSH 桌面版已安装并启用本插件的前提下，启动 DSH 后 **60 秒内**调度器进入运行态（`GET /api/dsh-todos-diy/health` 返回 `scheduler.running=true` 且 `lastTickAt` 在 60 秒内），用户无需打开任何面板或执行任何命令 |
| G2 | 循环规则灵活 | 用户可在 UI 内创建「每工作日 / 每周指定星期 / 每月指定日期 / 自定义 5 段式 cron」四类循环任务，并可为任意任务追加 `skipDates`（跳过日）与 `extraWorkdays`（补班日）；保存后下一次触发时间在 1 秒内可见 |
| G3 | 单次任务起止语义 | 用户可创建带 `startAt`（可选，不填默认取任务创建时间）与必填 `endAt` 的一次性任务；显式填写 `startAt` 时开始与结束各提醒一次，省略 `startAt` 时视为创建即开始、只提醒结束节点，两个节点各自最多提醒一次 |
| G4 | 状态持久化与恢复 | 关闭并重新启动 DSH 后，任务列表、启停状态、最近触发标记完整保留；**正常路径**下已触发节点不重复提醒，崩溃窗口内允许至多一次重复且可在 `deliveries` 追溯；超过 `graceMinutes` 的错过节点标记 `missed` 而不是静默补执行 |
| G5 | 多通道触达 | 到点后至少有一种用户可见的提醒方式生效：**默认 GUI 浮层（必有）**；浏览器支持且用户授权时可用**系统通知**（页面不可见时）；**不接入 Agent 会话**（D-02） |
| G6 | Agent 可管理 | Agent 可通过 9 个 `todo_reminder_*` 工具完成查询、创建、修改、删除、暂停、恢复、完成本次、稍后提醒与置顶，并收到结构化错误码 |
| G7 | 四视图、状态与优先级 | 主面板提供「未开始 / 进行中 / 已超期 / 已完成」四个页签及各自计数；任务阶段由 `startAt`/`endAt` 与当前时刻实时派生（不再有独立截止日期）；优先级按剩余时间实时计算；置顶任务固定在最上方，完成后自动取消置顶 |

### 1.3 非目标（v1 不做）

| 编号 | 非目标 | 说明 |
|---|---|---|
| NG1 | 团队协作与多用户共享任务 | v1 是单机、单用户的本地插件，不做账号、共享、指派 |
| NG2 | 节假日数据在线自动更新 | v1 **内置**中国法定节假日/调休数据（随插件版本发布，文件覆盖 2024–2027；2024–2026 为已公布正式安排，2027 待国务院公布后补丁）；不做联网自动抓取与热更新 |
| NG3 | 秒级/亚分钟级调度 | 精度为分钟级，轮询间隔 60 秒；最小粒度为 1 分钟 |
| NG4 | 跨设备同步 | 数据只存本机 `$DSH_HOME`，不做云同步 |
| NG5 | 复杂工作流编排 | 不做依赖关系、串并行、审批流；只做「到点提醒」 |
| NG6 | DSH 未运行时的系统级闹钟 | 插件运行在 DSH 进程内；DSH 完全退出时不会提醒，恢复后按 `graceMinutes`/`missed` 规则处理，不承诺像系统闹钟一样在关机或未登录时触发 |

## 2 角色与场景

### 2.1 角色

| 角色 | 描述 | 主要诉求 | 与本插件的关系 |
|---|---|---|---|
| 最终用户 | 综合管理岗人员，日常使用 DSH 桌面版处理文档与会话 | 打开 DSH 就能看到今天该做什么；不漏提醒、不被重复提醒打扰 | 通过侧边栏面板、浮层、Agent 会话使用 |
| 开发者 | 维护本插件的工程师 | 可测试、可维护、升级 DSH 不崩 | 编写宿主半、客户端半、测试 |
| DSH 运行时 | Cordis 插件框架 + Agent 会话 + 存储 + Web 服务 + 通知能力 | 按契约加载插件、注入服务、管理生命周期 | 提供 `ctx.*` 服务与 slot 挂载点 |

### 2.2 典型场景

| 编号 | 场景 | 规则 | 预期结果 |
|---|---|---|---|
| S-A | 每工作日晨间待办 | 周一至周五 09:00 | 每个工作日 09:00 弹一次浮层；周六周日不弹 |
| S-B | 月度材料提交 | 每月 1 号、30 号 09:00 | 1 号与 30 号各提醒一次；2 月无 30 号时按默认 `monthlyOverflow:"lastDay"` 顺延到 2 月 28 日（仅显式 `skip` 时跳过） |
| S-C | 周例会 | 每周一 10:00 | 每周一 10:00 提醒；遇 `skipDates` 中的日期跳过 |
| S-D | 单次任务起止 | 2026-11-05 14:00 开始、18:00 结束，两个节点都提醒 | 14:00 弹「任务开始」，18:00 弹「任务结束」；各只弹一次 |
| S-E | 重启恢复 | 用户在 09:30 重启 DSH，09:00 的提醒已触发 | 重启后不重复弹 09:00；下一次为次日 09:00 |
| S-F | 错过处理 | DSH 在 09:00 时未运行，10:30 才启动 | 09:00 的 occurrence 标记 `missed`，不补弹；若配置宽限 5 分钟且 09:03 启动则正常补弹一次 |
| S-G | 临时停用 | 用户休假一周，暂停某条工作日提醒 | 暂停期间不触发；恢复后从下一个未来时刻继续，不回填 |
| S-H | Agent 代建 | 用户在会话里说「每周五下午 5 点提醒我交周报」 | Agent 调用 `todo_reminder_create`，返回任务 id，面板立即可见 |

## 3 术语表

| 术语 | 英文 / 字段 | 定义 |
|---|---|---|
| 任务 | Task | 一条提醒配置及其状态的集合，是插件的核心数据单元 |
| 循环任务 | recurring task | 按规则重复产生的任务，每次产生一个 occurrence |
| 单次任务 | once task | 只有一组开始/结束时间、不重复的任务 |
| 发生点 | Occurrence | 任务在某个具体时刻应当触发的一次事件，含 `taskId + at + phase` 唯一键 |
| occurrenceKey | `occurrenceKey` | 去重主键，格式 `taskId@ISO时间`，单次任务追加 `#start` 或 `#end` 后缀；同一 key 只提醒一次 |
| 触发点 | trigger / phase | 单次任务的提醒节点：`start`（开始）、`end`（结束）；`phase` 仅用于 occurrence 节点，不用于任务状态 |
| 任务阶段 | stage | 任务在时间轴上的派生位置：`notStarted` / `inProgress` / `overdue` / `done` / `paused` / `recurring` / `archived`；读时计算、不落盘 |
| 规则 | Rule | 循环任务的重复定义：preset + 规范化 cron + 时区 + 例外日 |
| 预设 | preset | 面向用户的规则模板：`workdays`（工作日）、`weekly`（每周）、`monthly`（每月）、`custom`（自定义 cron） |
| 规范化 cron | canonical cron | 将用户输入规范化后的标准 5 段式 Vixie 表达式，存储只保存这一形式 |
| 例外日 | exception dates | `skipDates`（跳过）与 `extraWorkdays`（补班），均按任务时区的本地日期 `YYYY-MM-DD` 表示 |
| 错过 | missed | 发生点已过期且超过宽限期仍未触发，被标记为错过而非补执行 |
| 宽限期 | graceMinutes | 允许补触发的时间窗，默认 5 分钟，`0` 表示零容忍 |
| 触发标记 | fired | 发生点已投递的持久标记；循环任务用 `lastOccurrenceKey`，单次任务用 `firedStart`/`firedEnd` |
| 投递 | delivery | 把提醒内容送到某个通道（overlay / system）的动作 |
| 通道 | channel | `overlay`（浮层）、`system`（系统通知）两种提醒方式；v1 不做 `session` |
| 免打扰 | DND (Do Not Disturb) | 指定时间段内不弹浮层/通知，改为静默入队 |
| 浮层 | overlay | 通过 `shell.overlay` slot 渲染、覆盖整个框架的提醒层 |
| 节假日表 | holidayCalendar | 随插件发布的内置中国法定节假日/调休数据（文件覆盖 2024–2027；2024–2026 正式、2027 待公布），纯函数查询、不联网 |
| 工作日 | workday | 中国法定工作日：周一至周五且非法定节假日，并包含调休补班的周末 |
| 原子写 | atomic write | 先写临时文件再 `rename` 覆盖，读方只会看到旧文件或完整新文件 |
| 面板 | panel | 通过 `main` keyed slot 注册的整页 UI，对应侧边栏条目 |
| NS | locale namespace | 客户端文案命名空间，本插件统一为 `todos-diy`，用客户端 `ctx.locale.register(NS, { zh, en })` 注册（宿主半无 `ctx.locale`） |
| 宿主半 | host half | 运行在 DSH 主进程的插件代码，`package.json` 的 `main` / `exports["."]` |
| 客户端半 | client half | 运行在浏览器/渲染进程的 bundle，`exports["./client"]` + `dsh.client.platform="web"` |

## 4 现状与约束（DSH 实测）

本章全部结论来自本机安装的 DSH 0.2.1-rc.3（macOS 桌面版）实机核对，不是推测。实现时以本章为准；若 DSH 升级后行为变化，需重新核对并更新本节。

### 4.1 本机实测环境

| 项目 | 实测值 | 备注 |
|---|---|---|
| DSH 版本 | 0.2.1-rc.3 | 桌面版，`@deepseek-ai/dsh` 包版本一致 |
| 操作系统 | macOS | 桌面版，profile 位于 `~/.dsh/profiles/desktop` |
| 开发 shell Node | v22.23.2 | `node -v` 实测 |
| 桌面 runtime 自带 Node | 24.21.0 | `Resources/runtime/versions.json` |

| DSH 主目录 | `$DSH_HOME` 优先，否则 `~/.dsh` | 插件私有数据应落在 `$DSH_HOME/<plugin>/` |

### 4.2 插件形态

一个 npm 包 = **宿主半 + 客户端半 + 配置层** 三部分：

| 部分 | 声明位置 | 作用 |
|---|---|---|
| 宿主半 | `package.json` 的 `main` 或 `exports["."]` | 在 DSH 主进程执行 `apply(ctx, config)` |
| 客户端半 | `exports["./client"]` + `dsh.client.platform = "web"` | 浏览器端 bundle，由 `window.__ModuleLoader__` 加载 |
| 配置层 | `dsh.bundle.patch` 指向 `cordis.patch.yml` | 向 profile 组合插入插件 loader 行 |

`cordis.patch.yml` 的格式是顶层 YAML 数组，用 `- insert: [{ id, name, config }]` 插入一行。`id` 是行标识，用户可在自己的 `~/.dsh/profiles/desktop/cordis.patch.yml` 里按 `id` 做定向覆盖（改 `config` 或 `disabled: true`）；**`config` 是整体替换而非深合并**，覆盖时必须写全想保留的字段。

```yaml
- insert:
    - id: todos-diy
      name: 'dsh-todos-diy'
      config:
        tickIntervalMs: 60000
        timeZone: Asia/Shanghai
        defaultChannels: [overlay]
```

### 4.3 客户端 bundle 与 slot

客户端 bundle 必须手写为如下形态（`id` 必须**严格等于包名**，否则 loader 报 `loaded without registering ... via __ModuleLoader__.load`）：

```js
window.__ModuleLoader__.load({
  id: 'dsh-todos-diy',
  factory(require) {
    const React = require('react');
    return {
      inject: ['slots', 'locale'],
      apply(ctx) {
        // 注册 slot、样式、字典
      },
    };
  },
});
```

约束与事实：

1. **只能 `require` 平台冻结模块表里的模块**（`react` 可用）；不得 import 其它 Harness Client 包，不得写业务构建依赖。
2. `dsh.client.immediately: true` 只让 bundle 进入**首屏预取层**（`prefetchImmediateTier()` 调 `modules.prefetch()`），用于降低浮层首次出现延迟；它**不决定** bundle 是否物化或插件是否激活——已启用的客户端插件在 boot 阶段都会 `create`。本插件建议设置该字段以改善首次提醒延迟，但浮层能否常驻取决于 slot 是否注册，与 `immediately` 无关。
3. 可用 slot（本插件使用三个）：

| slot | 注册形态 | 用途 |
|---|---|---|
| `sidebar.panellist` | `ctx.slots.inject('sidebar.panellist', () => ctx.slots.register({ name:'sidebar.panellist', id:'todos-diy', order:30, label:()=>t('entry.label') }, Glyph))` | 侧边栏入口图标 |
| `main` | `ctx.slots.inject('main', () => ctx.slots.register({ name:'main', key:'todos-diy', locale:NS }, Panel))` | 中央主面板整页 UI |
| `shell.overlay` | `ctx.slots.inject('shell.overlay', () => ctx.slots.register({ name:'shell.overlay', id:'todos-diy-overlay', order:60, locale:NS }, ReminderOverlay))` | 覆盖整个框架的提醒浮层 |

`sidebar.panellist` 的 `id` 必须与 `main` 的 `key` 相同，shell 才会把侧边栏点击接到该面板。`shell.overlay` 是帧级浮层，与当前选中的面板无关，DSH 打开着就能看到。

### 4.4 宿主服务与 HTTP 准入

| 能力 | API | 关键约束 |
|---|---|---|
| 工具注册 | `ctx.tools.register(defineTool({...}))` 或原始 JSON Schema 定义 | `defineTool` 支持类型化参数/输出、`timeoutMs`、`presentCall`/`presentResult`；schema 会进入系统提示 |
| 定时器 | `ctx.interval(cb, ms)`（来自 `cordis-plugin-timer`） | 返回 disposer，随 fiber 自动清理；`ctx.timeout` 为单次 |
| 资源生命周期 | `ctx.effect(fnOrDisposer, label)` | fn 可返回 disposer；插件卸载时自动执行 |
| 日志 | `ctx.logger.info/warn/error` | 不要用 `console.log` 污染宿主日志 |
| Web 路由 | `ctx.webServer.register({ kind:'exact', path:'/api/<plugin>/...', handler })` | 在 `ctx.inject(['webServer'], cb)` 内注册，并用 `ctx.effect` 包裹 disposer |
| 请求准入 | `connection.requestRejection({ headers: req.headers })` | 返回 `undefined`（放行）/ `401`（未认证）/ `403`（Host/Origin 不可信）；**exact 路由先于官方 `/api` prefix 匹配，必须显式委托**，不能依赖官方鉴权自动生效 |

> 说明：**`ctx.locale` 不是宿主服务**，它由客户端 `dsh-client-locale` 插件在浏览器侧 `ctx.provide("locale")`；宿主半不要调用，宿主返回错误码即可，客户端用字典翻译。

`connection` 服务缺失时必须回退**纯回环检查**：`socket.remoteAddress` 为 `::1` / `127.*` / `::ffff:127.*`，`Host` 头解析出的主机为 `localhost` / `[::1]` / `127.*`，且 `sec-fetch-site !== 'cross-site'`。401 表示需要已登录的浏览器会话，403 表示来源不可信，二者要返回不同错误信封。

### 4.5 持久化能力

| 方案 | 事实 | 适用判断 |
|---|---|---|
| `ctx.storageDomain.open(defineDomain({name, version, tables}))` | 官方能力：schema 校验 + 原子持久 + `domain/changed` 事件 + 同步读 | 需要 `storage-domain` 与 `storage-json` 后端路由；依赖 `@deepseek-ai/dsh-storage-domain`，属于官方包耦合 |
| 单 JSON 文件 + `tmp + rename` | 第三方插件普遍采用（dsh-todos 0.1.3 即此方案） | 零依赖、可整库导出、易调试；需自行处理损坏备份与并发写 |
| `@deepseek-ai/dsh-home-paths` | `resolveDshHome()` / `dshHomePath()` 解析 `$DSH_HOME` 优先、否则 `~/.dsh` | 只是路径工具库，不提供存储；可作为 devDependency 或自行实现同等逻辑 |
| `@deepseek-ai/dsh-atomic-write` | `writeFileAtomic` + `withFileLock`，不保证 fsync | 可用作可选实现参考；零依赖自实现等价逻辑即可 |

**v1 选型**：单 JSON 文件原子写，路径 `$DSH_HOME/dsh-todos-diy/tasks.json`，宿主半不 import 任何 `@deepseek-ai/*` 运行时包。理由见 7.1。

### 4.6 内置 `@deepseek-ai/dsh-schedule` 的能力边界

DSH 已内置提醒服务与「自动化任务」页面，这是本插件最重要的现状约束。实测结论：

**已具备：**

1. 宿主服务 `ctx.schedule`，提供 `create / list / catalog / history / delete / update`，任务持久化在 `schedule` domain（JSON 后端落在 `schedule.json`）。
2. 选择器六选一：`at`（严格未来 ISO）、`after_seconds`、`every_seconds`（≥60）、`daily{time:"HH:mm:ss", time_zone}`、`weekly{time, time_zone, weekdays:[1..7]}`、`cron{expression, time_zone}`。
3. cron 为标准 5 字段 Vixie：`minute 0-59, hour 0-23, dom 1-31, month 1-12, dow 0-7`（0 与 7 都是周日）；支持 `*`、单值、`a-b`、`*/n`、`a-b/n`、逗号列表；拒绝 `L/W/#`、月份/星期英文名、`@daily` 宏、6 字段；创建时规范化表达式。
4. 任务绑定创建它的 Session；到期以 **follow-up 消息注入原会话**（会恢复冷会话）；一次性任务投递后 `status=inactive`，循环任务推进到下一个未来目标。
5. 客户端有「自动化任务」页面（侧边栏入口、任务列表、详情、运行记录、右侧栏任务页签、会话页头提醒按钮）。
6. 内置工具 `schedule_create / schedule_list / schedule_update / schedule_delete` 挂在 `standard` / `cordis` / `ptc` preset；`minimal` 没有。

**明确不具备（决定了本插件不能直接复用）：**

| 缺口 | 实测行为 | 对本插件的影响 |
|---|---|---|
| 无暂停/恢复 API | `inactive` 任务不能 `update`（返回 `schedule_ended`），只能 `delete` | 无法实现 R4「临时关闭某条循环任务」 |
| 无法单独配置「结束节点」提醒 | 选择器只有单一触发时刻，没有 start/end 双节点语义 | 无法实现 S2 |
| 错过策略不可控 | 每个循环任务**只补最近一次**错过的 occurrence，仍会补发 | 与「不静默补执行」的 S4 目标不同 |
| 非 exactly-once | 崩溃可能重复投递；无自动重试 | 无法承诺严格防重复 |
| 规则不可暂停、不可立即执行 | UI「规则」只支持修改活动任务的名称/指令/时间 | 管理能力不足 |
| 无创建表单 | UI「新建」会打开新会话让模型创建 | 不能作为完整 GUI 产品形态 |
| 无内置通知中心 | 未发现官方页面通知/系统通知服务 | N2 需要自行实现 |
| 不便自定义任务字段 | 任务模型固定（title/prompt/selector/status） | 无法承载 `skipDates`、`extraWorkdays`、`holidayCalendar` 等 |

**结论**：内置 `ctx.schedule` 是「会话级一次性/周期提醒」的通用底座，不是「综合管理岗工作待办」的产品底座。v1 采用**自研轻量调度**（D-01 已拍板），任务不绑定会话、不共享内置任务存储，也不复用其 follow-up 投递（D-02：不接入 Agent 会话）。

### 4.7 兼容性约束

1. 官方包 `peerDependencies` 多为**精确版本** `0.2.1-rc.3`；第三方插件若声明 peer，会被锁死在单一预发布版本。
2. `engines.dsh` 是**会被强制校验**的兼容声明：`dsh-app-boot` 的 `unmetRequirements()` 在清单含 `engines.dsh` 时**只按该范围判定并忽略 peerDependencies**，不满足则拒绝加载（`incompatible-version`，可用 `dsh plugin allow-version` 精确豁免，豁免不继承）。因此 v1 只写 `"^0.2.1-rc.3"`，不写跨 minor/major 线的宽范围。
3. **预发布语义取决于 evaluator**：`dsh-app-boot` 用 `semver.satisfies(runtime, range, { includePrerelease: true })` 求值。在该模式下 `^0.2.0-rc.1` 与 `>=0.2.0-rc.1 <0.3.0` **确实匹配** `0.2.1-rc.3`（实测）；真正不跨的是 **minor/major 线**：`^0.1.1-rc.1` 不匹配 `0.2.x`，`^0.2.x` 不匹配 `0.3.0-rc.1`。若改用 npm 默认（不带 `includePrerelease`），预发布版本会被范围排除，因此不要照搬 npm 的默认语义。
4. 声明 `engines.dsh` 后，**peerDependencies 不再参与兼容判定**；若需兼容旧线，应改用多 comparator（如 `"^0.1.0-rc.6 || ^0.2.1-rc.3"`），并逐条用上述 includePrerelease 语义实测，不照抄网络示例。
5. 官方 cron 方言即标准 5 字段 Vixie；不要引入 6 字段秒级 cron，否则与 DSH 语义分叉。

## 5 功能需求

### 5.1 编号与优先级规则

- 需求编号统一为 `F<章>.<条>`；优先级 **P0 = 首个可用版本必须**，**P1 = 首个版本应做、可延期一个迭代**，**P2 = 增强项、可后续版本**。
- 每条需求都给出「验收口径」，验收口径必须是**可观察、可判定**的行为，不写感受性描述。
- 涉及时间的验收，统一以任务时区（默认 `Asia/Shanghai`）的本地时间表述；实现内部一律用 UTC 毫秒 + IANA 时区换算。

### 5.2 F1 任务模型与状态机（P0）

| 编号 | 优先级 | 需求描述 | 验收口径 |
|---|---|---|---|
| F1.1 | P0 | 任务必须具备统一模型：`id`、`title`、`description`、`kind`（`recurring` / `once`）、`status`、`pinned`、`doneAt`、`rule` 或 `once`、`notify`、`state`、`createdAt`、`updatedAt`、`revision`；**不含 `dueDate`（D-25：截止时间统一由 `endAt` / `rule.time` 承载）**；**不含 `sessionId`**（D-02：不接入 Agent 会话）。**`TaskInput`（可写）与 `TaskView`（只读投影）必须分离**：`TaskView` 额外含 `stage`、`priority`、`fired`、`nextAt`、`timeZone`、`utcOffset`、`overdueDays`、`overdue`、`state`、`archivedQuarter` 等派生/历史字段 | `GET /tasks/get` 的 `TaskView` 与 `POST /tasks/create` 的 `TaskInput` 按白名单比较：只比较 title/description/kind/rule/once/notify/pinned 等可写业务字段，排除 id/revision/createdAt/updatedAt/status/doneAt/state/stage/priority/fired/nextAt/timeZone/utcOffset/overdueDays/overdue/archivedQuarter；缺少必填字段返回 `invalid_argument` |
| F1.2 | P0 | 任务状态机必须为：`active`（启用）↔ `paused`（暂停）；`active` → `done` **仅限 `kind=once`**（完成/归档）；`done` → `active`（撤销完成/恢复）；任意状态 → `archived`（删除进回收站）；`archived` → `active`（恢复）。**循环任务永远不进入 `done`：`complete` 只推进当前 occurrence，循环任务只有 `active/paused/archived`**；`done` 只能由用户或 Agent 显式完成，不因时间到期自动进入（D-25） | 非法转移（如 `paused` 直接 `done`、`archived` 直接触发、循环任务直接 `done`）返回 `invalid_state`，且状态不变；单次任务过了 `endAt` 未完成时 `status` 仍为 `active`、`stage="overdue"`；`done→active` 撤销后 `doneAt=null`、`pinned=false` |
| F1.3 | P0 | 每个任务维护 `state`：`lastFiredAt`、`lastOccurrenceKey`、`fired`（只读派生）、`firedStart`、`firedEnd`、`firedStartAdvance`、`firedEndAdvance`、`missedStart`、`missedEnd`、`missedAt`、`missedCount`、`snoozeUntil`、`completedOccurrenceKey` | 触发后 `lastOccurrenceKey` 必须等于该 occurrence 的 key；同一 key 再次 tick 不产生第二次投递；省略 `startAt` 创建的单次任务 `firedStart=true` |
| F1.4 | P0 | 去重键必须全局唯一：`occurrenceKey = taskId + '@' + at.toISOString() + (phase ? '#' + phase : '')`，即固定 UTC `YYYY-MM-DDTHH:mm:ss.sssZ`；持久化以该键为准，不以「当前时间窗口」为准 | 同一任务同一时刻连续 tick 3 次，投递次数为 1；把系统时间回拨 5 分钟后再次 tick，投递次数仍为 1；任务修改时区后历史 key 不变 |
| F1.5 | P1 | 任务支持软删除（`archived`）与硬删除（`purge`）；软删除保留 30 天，超期由每日清理任务物理删除 | 删除后任务从默认列表消失、不再触发；`GET /snapshot?includeArchived=1` 可见；30 天后自动消失 |
| F1.6 | P1 | 任务必须带 `revision` 乐观锁，更新请求需携带 `expectedRevision`；不匹配返回 `conflict` 并附当前 `revision` | 两个并发更新同一任务，后到者返回 `conflict`，数据不被覆盖 |

### 5.3 F2 循环规则（P0）

| 编号 | 优先级 | 需求描述 | 验收口径 |
|---|---|---|---|
| F2.1 | P0 | **工作日规则（跟随法定节假日，D-04）**：默认按「中国法定工作日」触发——周一至周五**且**非法定节假日，并包含调休补班的周六/周日；底层 cron 仍规范化为 `0 9 * * 1-5`，但求解 `nextOccurrence` 时叠加 `holidayCalendar` 过滤；任务可切换为「仅周一至周五，不看节假日」 | 创建 `workdays 09:00`：2026-10-01（国庆，周四）不触发；2026-10-10（调休上班，周六）触发；2026-10-30（周五）触发；切换到「固定周一至周五」模式后 10-01 恢复触发 |
| F2.2 | P0 | **每周规则**：用户选择 ISO 星期集合（1=周一 … 7=周日）与时间；底层规范化为 `0 9 * * 1` 这类表达式；星期集合去重升序 | 选择「每周一 10:00」后，仅周一 10:00 触发；选择多选「周一、周三」后两天各触发一次；空集合返回 `invalid_argument` |
| F2.3 | P0 | **每月规则（月末顺延，D-05）**：用户选择 1–31 的日期集合与时间；底层规范化为 `0 9 1,30 *`；**日期不存在于当月时顺延到当月最后一天**（`monthlyOverflow:"lastDay"` 为默认），不报错、不跨月；可选 `"skip"` 改为跳过该月 | 创建「每月 1 号、30 号 09:00」后：2026-02 触发 1 号与 **2 月 28 日**；2026-04 触发 1 号与 **4 月 30 日**；「每月 31 号」在 2026-02 触发 2 月 28 日；切换 `skip` 后 2 月只触发 1 号 |
| F2.4 | P1 | **自定义 cron**：接受标准 5 字段 Vixie 表达式，字段范围与 DSH 内置一致；拒绝 `L/W/#`、英文名、宏、6 字段，错误码 `invalid_cron` 并指出字段 | 输入 `0 9 * * 1-5` 保存成功；输入 `0 9 L * *` 返回 `invalid_cron`；输入 `0 0 9 * * *` 返回 `invalid_cron` |
| F2.5 | P0 | **例外日（叠加在内置节假日之上）**：`skipDates` 中的本地日期不触发；`extraWorkdays` 中的本地日期即使规则不匹配也按规则时间触发；两者都优先于内置节假日表（用户手工覆盖优先）。两个列表按任务时区解释，格式 `YYYY-MM-DD`，去重升序 | 即使内置表已把 2026-10-01 标为假期，用户加 `extraWorkdays:["2026-10-01"]` 后当天仍触发；内置表把 2026-10-10 标为补班，用户加 `skipDates:["2026-10-10"]` 后当天不触发 |
| F2.6 | P0 | **时区**：每条任务独立保存 IANA 时区，默认 `Asia/Shanghai`；循环任务存 `rule.timeZone`，单次任务存 `once.timeZone`；规则匹配、`skipDates`、`holidayCalendar`、展示时间全部以该时区为准 | 同一 cron `0 9 * * *` 在 `Asia/Shanghai` 与 `Europe/London` 两条任务，分别在各自本地 09:00 触发（UTC 时刻不同）；新建 `Asia/Tokyo` 的 once 任务，`startAt/endAt` 按 Tokyo 解释 |
| F2.7 | P1 | **DST 语义**：本地时间不存在（春令时跳变）时跳过该次；本地时间重复（秋令时回拨）时只取较早的一次；不因时区数据变化重算历史 | 用 `America/New_York` 2026-03-08 02:30 的规则测试，该日不触发；2026-11-01 01:30 只触发一次 |
| F2.8 | P2 | **月末策略开关**：`monthlyOverflow` 取值 `"lastDay"`（默认）或 `"skip"`；`lastDay` 表示 29/30/31 不存在时顺延到当月最后一天 | 默认「每月 31 号」在 2026-02 触发于 02-28；显式设 `skip` 后 2 月不触发 |
| F2.9 | P2 | **规则预览**：保存前返回未来 5 次触发时间（`POST /rules/preview`），供 UI 展示 | 任意合法规则返回长度 ≤5 的 ISO 时间数组，严格升序，且与保存后实际触发一致 |

### 5.4 F3 单次任务起止语义（P0）

| 编号 | 优先级 | 需求描述 | 验收口径 |
|---|---|---|---|

### 5.6 F5 提醒触达（P0/P1/P2）

> **决策 D-02（已拍板）：v1 不接入 Agent 会话。** 提醒只走两条通道：`shell.overlay` 页面浮层（必有）与浏览器系统通知（页面不可见且已授权时）。原稿 N1「触发时拉起 Agent 会话」不在 v1 实现，相关能力留到 v1.1 评估；因此任务模型不含 `sessionId`，也不做会话绑定、follow-up、冷会话恢复。

## 7 技术框架

### 7.1 架构选型对比

**已拍板：D-01 选方案 A——自研轻量调度 + 自管持久化**（不依赖内置 `ctx.schedule`，也不走混合）。持久化介质在 A 内部再选：**JSON 原子写（推荐）** vs **SQLite（node:sqlite）**，见 7.7。

| 维度 | 方案 A：自研轻量调度（**已采纳**） | 方案 B：复用 `ctx.schedule`（不采纳） | 方案 C：混合（不采纳） |
|---|---|---|---|
| 任务模型 | 完全自定义，可承载 `skipDates`、`holidayCalendar`、`advanceMinutes`、`pinned` | 固定 title/prompt/selector/status，无法扩展 | 自研模型 + 内置调度影子任务，需双向同步 |
| 暂停/恢复 | 状态机原生支持 | **不支持**（inactive 不能 update，只能 delete） | 自研侧支持，但内置影子任务无法暂停，仍需删除重建 |
| 起止双节点 | 原生支持 `start`/`end`/`both` | 不支持，只能拆成两条一次性任务 | 可拆两条影子任务，但去重与一致性复杂 |
| 错过策略 | 可配 `graceMinutes`、可标 `missed`、可零回填 | 每个循环任务补最近一次错过，不可配 | 受内置语义污染，难以保证零回填 |
| 防重复 | `occurrenceKey` + 先落盘后投递，单进程内严格 | 非 exactly-once，崩溃可能重复 | 两套存储各自去重，跨崩溃一致性差 |
| 持久化 | 单 JSON 原子写，零依赖 | `storageDomain` + `schedule.json`，官方维护 | 双写，复杂 |
| UI | 完全自研，可做完整 CRUD 与浮层 | 只有「自动化任务」页，无创建表单、无暂停 | 自研 UI + 内置页面并存，入口重复 |
| 会话投递 | 不需要（D-02 不接入会话） | 现成（follow-up 原会话）但 v1 不用 | 不需要 |
| 开发成本 | 中（约 15–20 人日） | 低（约 5 人日）但关键需求做不到 | 高（约 25 人日），且受两侧约束 |
| 升级风险 | 低（零官方包依赖） | 低（官方维护）但 API 可能变 | 高（同时跟两套 API） |
| 结论 | **推荐** | 仅适合「会话内简单提醒」，不适合本产品 | 不推荐 |

**推荐理由**：

1. 原稿 R4（临时关闭）、S2（结束节点）、S4（错过不静默补执行）三项是**产品核心语义**，内置 `ctx.schedule` 明确不支持或语义相反，复用会导致需求无法验收。
2. 本插件是「工作待办」而非「会话提醒」，任务需要独立于会话存在，内置服务的会话绑定模型不匹配。
3. 自研单 JSON + 纯函数调度可做到零 `@deepseek-ai/*` 运行时依赖，规避预发布版本 peer 锁死问题，升级 DSH 时只需核对 `ctx` 服务契约。
4. **不接入 Agent 会话（D-02 已拍板）**：v1 只做浮层 + 系统通知，不需要 `sessionController`、`agent.followup` 或 `sessions.flush`，因此宿主半可以真正零 `@deepseek-ai/*` 依赖，也不会因模型轮次产生 token 成本。

### 7.2 推荐架构与数据流

```
┌──────────────────────────── DSH 主进程（宿主半） ────────────────────────────┐
│  apply(ctx, config)                                                         │
│    ├─ Store.load()        同步读 tasks.json → 校验/迁移 → 内存态           │
│    ├─ Repository          CRUD + 状态机 + 写队列（串行）                    │
│    ├─ Scheduler           ctx.interval(tick, 60s) + 立即 tick 一次          │
│    │    └─ resolveTick(tasks, now) → { fire, markMissed, nextWakeAt }       │
│    ├─ Delivery            overlay(outbox) / system(notification)            │
│    ├─ routes.ts           webServer exact 路由 + connection 准入            │
```

### 7.5 调度核心纯函数签名

```ts
/** 规则定义（与存储中的 rule 同构）。 */
export interface RecurrenceRule {
  preset: 'workdays' | 'weekly' | 'monthly' | 'custom';
  cron: string;
  timeZone: string;
  skipDates: string[];
  extraWorkdays: string[];
  monthlyOverflow: 'skip' | 'lastDay';
}

/** 一次应当触发的事件。 */
export interface Occurrence {
  taskId: string;
  at: Date;
  phase: 'start' | 'end' | 'advance' | null;
  key: string;                 // taskId@<UTC ISO 毫秒>Z[#phase]
  kind: 'recurring' | 'once';
}

/** Tick 计划：纯函数输出，不含 IO。 */
export interface TickPlan {
  fire: Occurrence[];
  markMissed: Occurrence[];
  nextWakeAt: Date | null;
}

/** 解析并规范化 5 段式 Vixie cron；非法抛 CronError(code, field)。 */
export function parseCron(expression: string): CronSpec;
export function canonicalizeCron(expression: string): string;

/** 规则在 after 之后（严格大于）的下一个触发时刻；无下一次返回 null。 */
export function nextOccurrence(
  rule: RecurrenceRule,
  after: Date,
  timeZone: string,
): Date | null;

/** 任务在 (lastFiredAt, now] 区间内应处理的发生点；循环任务最多返回 1 条（最近一次错过/到点）。 */
export function dueOccurrences(
  task: Task,
  now: Date,
  lastFiredAt: Date | null,
): Occurrence[];

/** 全量任务的一次 tick 判定：到点触发、过期标记、下次唤醒时间。 */
export function resolveTick(tasks: Task[], now: Date): TickPlan;

/** 辅助纯函数。 */
/** 任务阶段：读时派生，不落盘（D-25） */
export type Stage = 'notStarted' | 'inProgress' | 'overdue' | 'done' | 'paused' | 'recurring' | 'archived';
/** 派生优先级：纯函数，不读写存储；单次按 endAt、循环按 nextAt，以当前时刻计算 */
export type PriorityKey = 'high' | 'mid' | 'low' | 'none' | 'paused';
export interface Priority {
  key: PriorityKey;
  remainingMinutes: number | null;   // 负数 = 已超期；null = 无时间目标/已暂停
}
export function derivePriority(task: Task, now: Date): Priority;
export function stageOf(task: Task, now: Date): Stage;

/** 四个阶段页签 + 循环/暂停筛选；counts 与 prioritySummary 同源，避免前端各算一遍 */
export type TaskViewName = 'notStarted' | 'inProgress' | 'overdue' | 'done' | 'recurring' | 'paused';
export interface TaskState {
  lastFiredAt: string | null;
  lastOccurrenceKey: string | null;
  firedStart: boolean;
  firedEnd: boolean;
  firedStartAdvance: boolean;
  firedEndAdvance: boolean;
  missedStart: boolean;
  missedEnd: boolean;
  missedAt: string | null;
  missedCount: number;
  snoozeUntil: string | null;
  completedOccurrenceKey: string | null;
}
export interface TaskView extends Omit<Task, 'state'> {
  stage: Stage;
  priority: Priority;
  fired: boolean;
  timeZone: string;
  utcOffset: string;
  nextAt: string | null;
  overdueDays: number | null;
  overdue: boolean;
  state: TaskState;
}
export interface ViewResult {
  items: TaskView[];
  counts: { notStarted: number; inProgress: number; overdue: number; done: number; paused: number; recurring: number };
  byKind: { once: number; recurring: number };
  totalDone: number;
  prioritySummary: { high: number; mid: number; low: number; none: number };
}
export function selectView(tasks: Task[], view: TaskViewName, now: Date): ViewResult;

/** 排序：置顶 > 优先级 > 结束时间（循环按 nextAt）；同分按标题 */
export function sortTasksForView(tasks: Task[], now: Date): Task[];

/** 最近未来阶段边界：全部非 archived 的 active/paused 任务（忽略当前 view/搜索），只取严格大于 serverTime 的 startAt/endAt/nextAt；done/archived 不参与；无则 null */
export function nextTransitionAt(tasks: Task[], now: Date): Date | null;

/** 完成动作：原子写 pinned=false + doneAt=now + status=done */
export function applyComplete(task: Task, now: Date): Task;

/** 节假日表：纯数据 + 纯函数；holidays 是「工作日中的假期」，workdays 是「周末中的补班」 */
export interface HolidayTable {
  schemaVersion: number;
  source: string;
  years: Record<string, { holidays: string[]; workdays: string[] }>;
}
export function loadHolidayTable(): HolidayTable;
export function isWorkday(table: HolidayTable, localDate: string): boolean;
export function isHoliday(table: HolidayTable, localDate: string): boolean;

export function isSkippedDate(rule: RecurrenceRule, localDate: string): boolean;
export function isExtraWorkday(rule: RecurrenceRule, localDate: string): boolean;
export function occurrenceKey(taskId: string, at: Date, phase?: 'start' | 'end' | 'advance'): string;  // 内部用 at.toISOString()
export function nextWakeAt(tasks: Task[], now: Date): Date | null;
```

语义约定：

1. `nextOccurrence` 必须严格 `> after`，避免边界重复；内部按 `timeZone` 的本地墙钟匹配 cron，再换算回 UTC。
2. `dueOccurrences` 对循环任务只返回**最近一个** `<= now` 且 `> lastFiredAt` 的 occurrence；停机跨越多个周期时，更早的通过 `markMissed` 处理，不进入 `fire`。
3. `resolveTick` 不读文件、不写文件、不取系统时间；`now` 由调用方注入，保证可测试、可回放。
4. `markMissed` 仅在 `now - occurrence.at > graceMinutes * 60_000` 时产生；宽限期内仍进 `fire`。
5. `nextWakeAt` 取所有 `active` 任务下一次目标的最小值；无任务时为 `null`，调度器可降频到每分钟一次的空转。

### 7.6 tick 算法（伪代码）

```ts
// scheduler.ts —— 唯一有副作用的编排层
let ticking = false;

async function tick(now: Date = new Date()): Promise<void> {
  if (ticking) return;                  // 重入保护：上一次 tick 未结束则跳过
  ticking = true;
  try {
    const tasks = repo.snapshotTasks();             // 内存态，O(n)
    const plan = resolveTick(tasks, now);           // 纯函数，无 IO

    // 0) 工作日前置：resolveTick 内部调用 isWorkday(holidayTable, date)，
    //    holidayCalendar="CN" 时叠加法定节假日/调休；"none" 时退回纯周一至周五
    // 1) 先标记错过（只改状态，不投递）
    for (const occ of plan.markMissed) {
      repo.markMissed(occ, now);
      logger.info(`todos-diy: missed ${occ.key}`);
    }

    // 2) 再投递到点事件：先 claim 落盘，再 enqueue，保证崩溃后不重复
    for (const occ of plan.fire) {
      const claimed = repo.claimOccurrence(occ, now);   // 比较并写入 lastOccurrenceKey/firedStart/...
      if (!claimed) continue;                            // 已被其它路径处理
      await delivery.enqueue(occ);                       // 写 outbox（浮层）+ 可选系统通知
    }

    // 3) 合并为一次原子写（无变化则不写）
    await repo.flush();

    // 4) D-25：不重算/不落盘 stage 与 priority。
    //    两者都是读时派生；tick 只处理提醒、错过与归档/清理等日级维护。

    // 5) 更新健康信息
    health.update({ lastTickAt: now, nextWakeAt: plan.nextWakeAt, tasks: tasks.length });
  } catch (error) {
    logger.warn(`todos-diy: tick failed: ${String(error)}`);
    health.update({ lastErrorAt: new Date(), lastError: String(error) });
    // 不抛出：下一轮 tick 继续，避免一次异常杀死调度
  } finally {
    ticking = false;
  }
}

// apply() 中的装配（严格顺序：load → ready → interval）
export function apply(ctx: Context, config: Config): void {
  const store = createStore(resolveDataDir());     // 同步读 + 校验/迁移
  const repo = createRepository(store, config);
  const delivery = createDelivery(ctx, config, repo);
  const scheduler = createScheduler(ctx, repo, delivery, config);

  ctx.effect(() => {
    const dispose = ctx.interval(() => void tick(), config.tickIntervalMs);
    void tick();                                    // 启动后立即补一次判定
    return () => {
      dispose();
      store.flushSync();                            // 卸载前同步落盘
    };
  }, 'todos-diy: scheduler');

  ctx.inject(['webServer'], (webCtx) => {
    webCtx.effect(() => {
      const routes = createRoutes(repo, { authorize: createAuthorize(() => webCtx.get('connection')) });
      const disposers = routes.map((r) => webCtx.webServer.register(r));
      return () => disposers.forEach((d) => d());
    }, 'todos-diy: routes');
  });

  ctx.inject(['tools'], (toolCtx) => {
    toolCtx.effect(() => {
      const disposers = createTools(repo).map((d) => toolCtx.tools.register(d));
      return () => disposers.forEach((d) => typeof d === 'function' && d());
    }, 'todos-diy: tools');
  });
}
```

### 7.7 持久化设计

#### 7.7.1 介质选型：JSON 文件 vs SQLite

| 维度 | 方案 J：单 JSON 原子写（**推荐**） | 方案 S：SQLite（`node:sqlite`） |
|---|---|---|
| 依赖 | 零依赖，只用 `node:fs` | Node 22.19+ 内置 `node:sqlite`（实验性，需 `--experimental-sqlite`？实测 22.23 直接可用但打 ExperimentalWarning） |
| 写入模型 | 全量重写 + `rename` 原子替换 | 事务 + WAL，行级更新 |
| 数据量 | 1 万条以内、单文件 ≤ 5MB 无忧 | 10 万条、频繁写入更优 |
| 并发 | 单进程串行队列；跨进程用 lock 文件 | 原生锁与 WAL，多进程更稳 |
| 查询 | 全量读入内存后过滤（1000 条 < 5ms） | SQL 索引，按 `endAt`/`status` 直接查 |
| 可读/可迁移 | 纯文本，可直接看、直接导入导出 | 需 `sqlite3` 或代码导出 |
| 崩溃一致性 | `rename` 保证不出现半截 JSON；掉电可能回退到上一版 | 事务保证原子，WAL 更可靠 |
| 备份 | 复制一个文件 | `VACUUM INTO` 或复制 db+wal |
| 迁移 | JSON `schemaVersion` + 迁移函数 | `PRAGMA user_version` + DDL 迁移 |
| 风险 | 单文件损坏影响全部数据（需备份重建） | `node:sqlite` 在 Node 22 仍标 Experimental，跨版本 API 可能变 |
| 结论 | **v1 采纳**：任务量级（个人待办，通常 < 1000 条）、零依赖、可读可导出，收益最大 | v2 备选：当任务 > 1 万条或需要多进程并发时切换 |

**推荐理由**：个人待办的数据量远低于 JSON 的瓶颈；JSON 单文件让「导入导出 / 备份 / 排障」变成一次文件复制，且不引入实验性 API。SQLite 的优势在数据量与并发，v1 用不上，反而增加迁移与兼容成本。

#### 7.7.2 JSON 方案细节

| 设计点 | 方案 |
|---|---|
| 路径 | `$DSH_HOME/dsh-todos-diy/tasks.json`；`$DSH_HOME` 为空/空白时用 `path.join(os.homedir(), '.dsh')` |
| 读取 | `apply()` 中同步 `readFileSync`（文件 > 2MB 时改为异步预加载，启动期先空态可用，避免阻塞宿主）；文件不存在视为空状态，不报错 |
| 写入 | `writeFile(tmp)` → 可选 `fsync` → `rename(tmp, target)`；`tmp` 与目标同目录，保证同一文件系统 |
| 并发 | 单进程内 Promise 队列串行；跨进程用 `tasks.lock`（PID + 时间戳），发现存活 PID 时第二个实例降级为只读（读路由可用，写路由返回 `read_only` 409），浮层不轮询 `/due` |
| 校验 | 读取后用 `validateState()` 逐字段校验；失败走 F6.7 备份重建 |
| 迁移 | `migrations: Array<(state: any) => State>`，从 `state.schemaVersion` 顺序执行到 `SCHEMA_VERSION` |
| 备份 | 覆盖前保留最近 1 份 `tasks.json.bak`；损坏时另存 `tasks.json.corrupt.<ts>` |
| 大小 | 主文件建议 ≤ 5MB；`deliveries` 只保留最近 1000 条 / 90 天，超出裁剪；已完成任务按季度移出主文件，进一步控制体积 |
| 归档目录 | `$DSH_HOME/dsh-todos-diy/archive/`，含 `index.json` + `completed-YYYY-Qn.json`；每个文件使用同一 `SCHEMA_VERSION=2`，任务带 `archivedQuarter` |
| 归档触发 | 每个季度首个 tick（本地时区 1/4/7/10 月 1 日 00:00 之后）执行一次 `archiveCompleted()`；幂等，按 `doneAt` 季度分组 |
| 归档顺序 | ① 写归档文件 tmp+rename → ② 重写主文件移除该批 → ③ 更新 index.json；崩溃在 ①→② 之间时启动对账按 id 去重 |
| 归档查询 | `GET /archive?quarter=2026-Q4&limit=50&cursor=`；`GET /archive/index` 返回季度列表 |
| 归档恢复 | `POST /tasks/restore {id}` 支持归档任务：从归档移回主文件，`status="active"`、`doneAt=null`、`archivedQuarter=null` |
| 导出 | `GET /export` 返回完整 JSON；导入前生成 `tasks.json.bak.<ts>` |

### 7.10 Agent 工具实现要点

1. 工具用**原始 JSON Schema** 注册，不 import `defineTool`，保持宿主半零运行时依赖；如需类型化，可在 `devDependencies` 放 `@deepseek-ai/dsh-tools` 并用 `import type`（编译后擦除）。
2. 工具不需要 `exec.agent`：任务不绑定会话（D-02），无 agent 上下文也能正常工作。
3. 工具描述必须包含：时区语义（默认 `Asia/Shanghai`）、cron 方言（5 字段 Vixie）、单次任务默认起止都提醒（D-03）、会议类可关闭结束提醒（`notify.endReminder=false`）、暂停/恢复与 `complete` 的区别。
4. 工具返回 `TaskView`（不含内部 `deliveryError` 等噪声字段），错误码与 HTTP API 一致。
5. 工具注册放在 `ctx.inject(['tools'], cb)` 内，disposer 由 `ctx.effect` 管理。

## 8 边界条件与失败模式

### 8.1 时间与规则

| 场景 | 触发条件 | 预期行为 | 用户可见结果 |
|---|---|---|---|
| 每月 30 号遇 2 月 | `monthly` 规则含 30/31 | 默认 `monthlyOverflow:"lastDay"`：2 月触发 2 月 28 日；仅显式 `skip` 时该月跳过、3 月 30 日正常 | 默认 2 月 28 日提醒；`skip` 时 2 月无提醒 |
| 闰年 2 月 29 日 | `monthly` 含 29 | 闰年触发，平年跳过 | 2028-02-29 提醒；2027-02 无 |
| DST 春令时缺口 | 本地 02:30 不存在 | 跳过该次，记录 `skippedByDst` | 当天无提醒；次日正常 |
| DST 秋令时重叠 | 本地 01:30 出现两次 | 只取较早一次 | 只提醒一次 |
| 系统时间回拨 | 用户手动改早 1 小时 | 不重复触发已 `fired` 的 occurrence；已记录的未来 occurrence 保持原 key，后续按新时间重新计算 | 无重复提醒；`health` 记录 `clockWentBack` |
| 系统时间前跳 | 用户手动改晚 3 天 | 跨过的 occurrence 中超过 `graceMinutes` 的全部 `missed`（最多记录 50 条），不补发；宽限期内的最近一次可补触发 | 浮层最多补弹 1 条；任务详情显示「错过 N 次」 |
| 时区数据变更 | 系统 ICU 更新导致规则偏移 | 不重算历史；只影响未来 | 历史记录不变 |
| cron 无未来目标 | 如 `0 0 30 2 *` | 保存前调用 `nextOccurrence` 预检；未来 20 年无触发则拒绝保存并返回 `invalid_cron`，不创建任务 | 用户看到「该规则不会再次触发」的字段错误；任务列表不新增 |
| 跨年 cron | `0 0 1 1 *`（每年 1 月 1 日 00:00） | `nextOccurrence` 正确跨年，返回下一年 1 月 1 日 | 12 月 31 日之后仍能算出下一次 |
| 休眠唤醒 | 系统睡眠 8 小时后唤醒 | 只执行 1 次 tick；`graceMinutes` 内的最近一个 occurrence 补触发一次，其余标 missed | 不连续刷屏；最多 1 条补发 |
| `lastDay` + `skipDates` 叠加 | `monthlyOverflow:"lastDay"` 且月末在 `skipDates` | `skipDates` 优先，跳过该月 | 该月无提醒 |
| 超大数据量 | 10000 条任务、`tasks.json` > 5MB | tick 仍按 60s 运行，单次 tick 计算 ≤ 20ms；读取超过 2MB 时改为异步加载，不阻塞宿主启动 | 面板加载有进度提示；提醒延迟 ≤ 60s |
| 客户端 HMR 重载 | 开发期连续热重载 10 次 | `shell.overlay` 只保留 1 个实例，样式与 locale 注册不重复 | 不出现重复浮层或重复文案 |
| 跨小时/跨天未重启 | DSH 一直开着，任务 16:00 开始、次日 00:00 跨天 | `stage`/`priority` 每次读取按当前 `now` 计算；客户端在最近边界刷新，兜底 60 秒 | 15:59 显示「未开始」，16:00:01 显示「进行中」；00:00 后「今天/明天」文案自动更新，无需重启或写库 |
| 时区与时间轴 | 任务时区 `Asia/Tokyo`，用户在北京看列表 | `startAt`/`endAt` 是绝对时刻；阶段比较用绝对时间，展示文案按任务时区换算 | 同一任务在不同设备时区下阶段一致，只有本地时间文案不同 |
| 置顶 + 超期 | 置顶任务的 `endAt` 已过且未完成 | 仍显示在「置顶」组最上方，同时带「超期」红标与高优先级 | 用户能立刻看到最紧急的置顶事项 |
| 完成置顶任务后撤销 | 置顶任务完成后悔改 | 完成时已清 `pinned`；「恢复为待办」不自动恢复置顶 | 需要用户重新点置顶 |

### 8.2 状态与并发

| 场景 | 触发条件 | 预期行为 | 用户可见结果 |
|---|---|---|---|
| 暂停中到期 | `status=paused` 且 occurrence 到期 | 不投递；`paused` 不产生 missed 记录 | 恢复后从下一未来时刻继续 |
| 删除后到期 | 任务已 `archived`/`purge` | 调度器跳过；迟到投递被丢弃 | 无提醒 |
| 并发编辑 | 两个窗口同时保存 | 后到者 `conflict` + 当前 `revision` | 提示「已被其它窗口修改，请刷新」 |
| 重复点击完成 | 浮层按钮连点 | `complete` 幂等，第二次返回 `changed:false` | 浮层只消失一次 |
| 稍后提醒与规则冲突 | 循环任务 09:00 提醒，用户 09:05 点 15 分钟后 | 09:20 临时提醒；次日 09:00 正常 | 两次提醒均在 |
| tick 重入 | 上一次 tick 未完成 | 直接跳过本轮，记录 `skippedTick` | 无重复投递 |

### 8.3 存储与恢复

| 场景 | 触发条件 | 预期行为 | 用户可见结果 |
|---|---|---|---|
| 文件损坏 | JSON 解析失败 | 备份 `tasks.json.corrupt.<ts>`，空状态启动，`health.lastRecovery.reason="corrupt"` | 面板空态 + 顶部警告条「数据文件损坏，已备份并重建」 |
| 磁盘写满 | `writeFile` 抛 `ENOSPC` | 本次写失败，保留内存态与旧文件；`health.storage.healthy=false` | 顶部警告「保存失败，请检查磁盘」 |
| 权限不足 | `EACCES` | 同上，不覆盖原文件 | 同上 |
| 版本过高 | `schemaVersion > SCHEMA_VERSION` | 拒绝启动调度，`health.storage.state="unsupported-version"` | 面板显示「插件版本过旧，请升级插件」 |
| 双进程 | 两个 DSH 实例同时打开 | `tasks.lock` 检测到存活 PID，第二个实例只读启动并提示 | 第二个实例顶部显示「另一个实例正在使用数据」 |
| 卸载时正在写 | 插件禁用 | `ctx.effect` disposer 先停止 interval，再 `flushSync()` | 无数据丢失 |
| 跨季度归档崩溃 | 归档写盘过程中 `kill -9` | 重启对账：按 `id` 去重，任务恰在一份文件中 | 无重复、无丢失 |
| 归档文件损坏 | `completed-2026-Q4.json` JSON 损坏 | 主文件不受影响；该季度标记 `corrupt`，可用 `.bak` 或跳过 | 「已完成」页签显示该季度不可读 |
| 归档目录被删 | 用户手动删 `archive/` | 启动时从 `index.json` 与文件名重建空索引；不阻塞启动 | 历史季度列表为空，不报错 |

### 8.4 投递与 UI

| 场景 | 触发条件 | 预期行为 | 用户可见结果 |
|---|---|---|---|
| 系统通知不可用 | 精简组合 / 浏览器不支持 | `system` 通道跳过，只走 `overlay`；`deliveries[].error` 记录 `not-supported` | 浮层正常；设置页显示「系统通知不可用」 |
| 无 Agent 会话 | v1 不绑定会话（D-02） | 所有任务只走浮层 + 可选系统通知 | 不产生任何会话消息，任务详情无「投递会话」字段 |
| 浮层未渲染 | 客户端 bundle 未物化 | 宿主仍写 outbox；下次打开面板时补拉 `/due` | 打开 DSH 后看到未读提醒 |
| 浏览器通知被拒 | `Notification.permission === 'denied'` | 静默跳过 `system` 通道，不重试 | 浮层正常；设置页显示「系统通知不可用」 |
| SSE 断线 | 网络/渲染进程重启 | 指数退避重连（1s/2s/5s/10s，上限 30s）；重连后按 `since` 补拉 | 浮层最多延迟 30 秒恢复 |
| 多窗口 | 同一 DSH 打开两个窗口 | 以 `occurrenceKey` 去重；一个窗口 ack 后另一个窗口下次轮询不再显示 | 不重复弹 |
| 浮层遮挡 | 同时 10 条到期 | 合并为「N 条待办提醒」摘要，展开列表 | 不遮挡全屏；可逐条处理 |

### 8.5 安全

| 场景 | 触发条件 | 预期行为 | 用户可见结果 |
|---|---|---|---|
| 跨站请求 | 第三方网页 `fetch` 本机 API | `requestRejection` 返回 403，或回环回退拒绝 | 返回 `forbidden` |
| 未登录浏览器 | 无有效会话 cookie | 401 `unauthorized` | 401 信封 |
| 超大请求体 | `Content-Length > 1MB` | 413 `payload-too-large` | 413 |
| 恶意导入 | JSON 含原型链字段/超长字符串 | schema 校验拒绝，不执行任何代码；字段截断并 warning | `invalid_argument` |
| 日志泄露 | description 含敏感信息 | 日志只打印标题前 20 字符与 id | 日志无全文 |

### 10.3 环境与工具

## 附录 B 与原稿差异说明

| 原表述 | DSH 实际约束 | v1 建议口径 |
|---|---|---|
| 「循环规则统一用 5 段式 Cron：`0 9 * * 1-5` / `0 9 1,30 *` / `0 9 * * 1`」 | DSH 内置 cron 是标准 5 字段 Vixie：支持 `*`、单值、`a-b`、`*/n`、`a-b/n`、逗号列表；拒绝 `L/W/#`、英文名、`@daily` 宏、6 字段；创建时规范化。原生 cron 无法表达「工作日但跳过法定节假日」 | 用户面用 **preset**（`workdays` / `weekly` / `monthly` / `custom`）降低认知成本；存储统一落**规范化 5 字段 cron**；例外日用独立 `skipDates` / `extraWorkdays` 列表，不塞进 cron |
| 「每月 1 号和 30 号提醒」 | 2 月没有 30 号，小月没有 31 号；cron 的 day-of-month 不匹配时直接跳过，不会顺延 | **已拍板 D-05：默认顺延到当月最后一天**（`monthlyOverflow:"lastDay"`）；「每月 30 号」在 2 月触发 2 月 28 日；可就任务改为 `"skip"` 跳过该月 |
| 「工作日」 | DSH 不内置中国法定节假日/调休数据；「工作日」在 cron 里只能表达为周一至周五 | **已拍板 D-04：跟随中国法定节假日与调休**。v1 内置 2024–2027 节假日表（`assets/holidays-cn-2024-2027.json`，2.3KB，源自 chinese-days@1.5.9），`holidayCalendar:"CN"` 默认；用户可用 `skipDates`/`extraWorkdays` 手工覆盖；可切换 `"none"` 退回固定周一至周五 |
