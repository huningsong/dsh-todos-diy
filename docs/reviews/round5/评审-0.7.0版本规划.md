# 评审-0.7.0 版本规划（桌面系统通知全局开关）

> 评审日期：2026-11-02
> 评审对象：[0.7.0 版本规划](../../planning/0.7.0版本规划.md)（179 行，状态「本规划」）
> 对照基线：[需求-v1.md](../../requirements/需求-v1.md) v1.19、`UX-决策记录.md` UX-30、当前 `main`（`0.6.0`，848 tests）
> 结论：**方向正确，但不能按当前文档直接开工；存在 4 个 P0 需求冲突 + 4 个 P1 设计缺口，需修订后再冻结。**

---

## 0. 总体判断

这个需求的**产品方向是成立的**：系统通知本质是设备级权限，不是任务属性；改成 `settings.desktopNotifications.enabled` 全局开关，比逐任务勾选更符合直觉，也简化任务编辑器。

但当前文档和 `需求-v1.md` v1.19 还没有真正对齐：

- 需求正文仍保留任务级系统通知的旧口径（F5.9/F5.10/F9.3/AC-14）；
- 0.7.0 规划把 F5.13/F5.14/F9.7/F10.14 列为 **P0 必做**，需求表却全部标成 **P1**；
- 全局设置的数据链路、生效链路、旧数据兼容和行为测试没有写完整。

因此当前状态是：**设计意图可保留，但必须先把下面的 P0/P1 修完；不建议直接进入 N0**。

---

## 1. P0 必须修改（开工阻断）

### R01 F5.2/F5.3/AC-14 仍是任务级系统通知口径

- **问题**：0.7.0 规划的核心规则是「全局开关开启 + 权限允许 + 后台」才发送系统通知（`0.7.0版本规划.md:77-88`）；但需求正文 F5.2/F5.3 仍只写「`Notification.permission === 'granted'` 且页面 hidden/失焦」，完全没有 `settings.desktopNotifications.enabled` 条件（`需求-v1.md:372-373`）。AC-14 仍用「任务 `channels=['overlay','system']` + 切后台」验收（`需求-v1.md:1294`）。
- **后果**：如果实现按 F5.2/AC-14 写，全局开关关闭时任务只要 channels 带 system 仍会发通知，直接违反 F5.13/F5.14；如果实现按新规则写，旧 AC-14 会失败，验收口径无法判定。
- **建议**：同步改 F5.2/F5.3/AC-14：
  - F5.2 增加「且 `settings.desktopNotifications.enabled === true`」；
  - AC-14 改为「全局开启且权限/后台满足时有系统通知；全局关闭时无系统通知」；
  - 增加「旧任务 channels 含 system 但全局关闭 → 只有浮层」的 AC（可与 AC-N03 合并）。

### R02 F5.9/F5.10 与 F5.14 互相矛盾

- **问题**：
  - F5.9（`需求-v1.md:379`）要求**任务编辑器**显示浏览器通知权限状态；
  - F5.10（`:380`）要求**任务编辑器**提供「测试系统通知」按钮；
  - F5.14（`:384`）却要求**任务编辑器不再显示系统通知复选框/状态/测试**；
  - UX-25/UX-26（`UX-决策记录.md:165-176`）也仍写任务编辑器；UX-30（`:205-207`）才规定全局开关。
- **后果**：实现方无法判断任务编辑器到底保留还是删除；测试无法同时满足两套验收。F5.10 的「测试系统通知」位置也与 F9.7（设置页）重复。
- **建议**：明确 **F5.9/F5.10 被 UX-30 取代**：
  - 将 F5.9/F5.10 的正文改为「历史口径（0.6.0）」或直接合并到 F9.7；
  - F9.7 承接「设置页权限状态 + 测试按钮 + 平台路径」；
  - UX-25/UX-26 顶部加「已被 UX-30 取代」标记，避免开发按旧决策实现。

### R03 F9.3 仍规定 `defaultChannels` 多选和任务级覆盖

- **问题**：F9.3（`需求-v1.md:461`）仍写「`defaultChannels` 多选（overlay 必选、system 可选）；任务级可覆盖；首次保存含 system 通道的任务时才请求权限」。这与 0.7.0 规划的「设置 UI 不再暴露 system 多选」「新任务 channels 固定 `['overlay']`」「任务级不再控制系统通知」直接冲突（`0.7.0版本规划.md:62-71`）。
- **后果**：设置页会同时出现「默认提醒方式」的 system 复选和新的「桌面系统通知」开关；F9.3 的验收也会要求任务级 system 生效，与新模型相反。
- **建议**：重写 F9.3 为**兼容字段说明**：
  - `defaultChannels` 保留在持久化/API 中供旧数据读取；
  - 设置 UI 只显示「浮层（必有）」+ 新的全局开关；
  - 新任务 `notify.channels` 固定 `['overlay']`；旧任务 system 值只保留、不参与生效判断。
  同时更新 F9.3 的验收口径，删除「关闭 system 后不再请求通知权限」这类旧语义。

### R04 P0/P1 优先级与需求表不一致

- **问题**：0.7.0 规划 §2.1 把 F5.13、F5.14、F9.7、F10.14 全部列为「**P0 必做**」（`0.7.0版本规划.md:33-40`）；但需求 v1.19 中这四项全部标为 **P1**（`需求-v1.md:383-384、465、483`）。
- **后果**：按需求表的 P0/P1 验收门，这四项可以延期；按版本规划又是 release blocker。测试/发布门无法统一。
- **建议**：二选一并同步：
  - 若 0.7.0 必须完成，把四项改 P0；或
  - 若坚持 P1，把规划 §2.1 改「本期必做（P1）」并明确 M 里程碑门槛不把它们算 P0。
  由于 0.7.0 主题就是这四件事，建议统一为 **P0**。

## 2. P1 应该修改（影响实现与验收）

### R05 F5.14 的「新任务固定 overlay」没有落到实现路径

- **问题**：F5.14 要求新任务 `notify.channels` 固定 `['overlay']`（`需求-v1.md:384`），但当前 `buildTask` 仍使用 `settings.defaultChannels`（`src/host/repoBuild.ts:52`）；`TaskDraft.channels` 仍可被表单/复制路径带入 system（`src/client/task-draft.ts:34、87、154`）。0.7.0 的 N0/N1/N2 写域没有明确包含 `repoBuild.ts`、`task-draft.ts`、`api.ts`。
- **建议**：明确：
  - 新任务创建时服务端强制 `notify.channels = ['overlay']`（忽略旧 `defaultChannels` 与旧 API 的 system 值，或按兼容策略保留但不用于投递）；
  - 编辑旧任务时保留 `notify.channels` 原值但不提供 UI；
  - 把 `repoBuild.ts`、`task-draft.ts`、`api.ts` 加入 N0/N2 写域，并补一条「旧任务编辑不改 system 字段」的测试。

### R06 `desktopNotifications` 的数据/API/客户端类型链路不完整

- **问题**：0.7.0 只定义了 `Settings` 里的 `desktopNotifications`（`0.7.0版本规划.md:57-71`），但当前实际链路至少涉及：
  - `src/host/state.ts` 的 `Settings` 与 `defaultSettings`（`:60-66、129-138`）；
  - `src/host/stateSettings.ts` 的 `coerceSettings`（`:26-56`）；
  - `src/host/validateSettings.ts` 的 patch 类型/校验（`:20-35`）；
  - `src/client/api.ts` 的 `SettingsPayload`（`:78-85`）；
  - `src/client/settings-modal.ts` 的 base/initial 与保存 payload（`:29、37-52`）。
  0.7.0 的 N0 写域只列 `state.ts/stateSettings.ts/validateSettings.ts/settings.test`，N2 没有 `api.ts`，会导致 TypeScript 编译错误或客户端拿不到新字段。
- **建议**：把上述文件加入 N0/N2 写域，并明确 `SettingsPayload.desktopNotifications` 的返回/可选性。

### R07 全局生效通道的归属未定义，`/due`/overlay 有实现漏点

- **问题**：0.7.0 说「宿主 `deliveryRecordsFor` / `/due` 生成卡片时按全局设置决定 system 通道」（`0.7.0版本规划.md:96-101`），但当前：
  - `buildReminderCard` 返回 `channels: task.notify.channels`（`src/host/delivery.ts:115`）；
  - `deliveryRecordsFor` 只按 `task.notify.channels.includes('system')` 生成 system 占位（`:145-148`）；
  - 客户端 overlay 又按 `card.channels.includes('system')` 决定是否发系统通知（`src/client/overlay.ts:93`）。
  如果只改 `deliveryRecordsFor` 不改 `buildReminderCard`，或只改 `/due` 记录不改卡片，系统通知仍然不会发。
- **建议**：在设计中明确唯一的 effective channel 来源：`buildReminderCard(task, occurrence, settings)` 或先在宿主算 `effectiveChannels` 再传入；`deliveryRecordsFor` 增加 settings/effective 参数；并加测试：全局开启 + 任务 channels 只有 overlay → 卡片含 system；全局关闭 + 任务 channels 含 system → 卡片不含 system。

### R08 AC-N01～AC-N08 没有并入主验收体系，测试计划不足

- **问题**：0.7.0 定义了 AC-N01～N08（`0.7.0版本规划.md:144-151`），但 `需求-v1.md` 的 §9 验收标准没有这些编号，§10 测试策略也没有对应映射；N3 只写「`test/*`」，没有具体测试文件/用例。现有 `test/delivery.test.ts:101-108` 仍断言「任务 channels 含 system 就加 system 占位」，`test/routes.test.ts:427-434` 仍断言 settings 的 `defaultChannels` 含 system，均会与 0.7.0 冲突。
- **建议**：把 AC-N 并入 §9（建议 AC-62～AC-69 或明确 AC-Nxx 为新增编号），并在 §10.2 建立 AC→测试映射：
  - 默认关闭只有浮层；
  - 全局开启 + 权限 granted + 后台 → system；
  - 全局关闭 + 旧任务 system → 仅 overlay；
  - 权限拒绝/不支持 → 开关保持 false；
  - 任务编辑器无 system 控件；
  - settings 缺失字段默认 false；
  - README/需求/UI 文案一致。
  同时更新 `delivery.test.ts`、`routes.test.ts`、`state.test.ts` 的旧断言。

### R09 「不升 schemaVersion」的兼容风险未说明

- **问题**：规划 §3.1 明确不升 `schemaVersion`（`0.7.0版本规划.md:69-71`），只增加可选 `desktopNotifications` 默认 false。旧版本插件读取新文件时，`coerceSettings` 会丢弃未知字段；如果用户在旧版本中修改任何设置，`desktopNotifications` 会被写回时丢掉，之后再升级回来用户的开关状态就丢了。
- **建议**：明确兼容策略：
  - 接受降级时丢失全局开关（在升级说明中写清楚）；或
  - 提升 `schemaVersion` 并为设置字段增加迁移；
  - 至少补「新文件被旧版本读取/写回」的回归测试，不能只测旧文件→新版本。

### R10 权限状态与保存交互未定义完整状态机

- **问题**：规划 §5.1 只说「开关开启时请求权限；拒绝→保持 false」（`0.7.0版本规划.md:105-119`），但没有定义：
  - 开关在请求权限前是否先视觉打开；
  - 用户授权后点「取消」是否持久化；
  - 权限后来被浏览器/系统撤销时，`enabled` 仍是 true 还是自动改 false；
  - 设置页「测试通知」在全局开关关闭时是否可用。
- **建议**：写出状态机（关闭/请求中/已开启/权限缺省/拒绝/不支持），并明确 `enabled` 是持久化意图、实际发送仍需 permission；补「授权后取消保存」「权限被撤销」的测试。

## 4. 对现有实现的影响清单

| 模块 | 当前行为 | 0.7.0 需要 |
|---|---|---|
| `src/host/state.ts` / `stateSettings.ts` | `Settings` 无 `desktopNotifications`，`defaultSettings`/`coerceSettings` 无该字段 | 增加字段、默认 false、coerce 兼容 |
| `src/host/validateSettings.ts` | 只校验 `defaultChannels/dnd/nlp` 等 | 增加 `desktopNotifications.enabled` boolean 校验 |
| `src/host/repoBuild.ts` | 新任务 channels 取 `settings.defaultChannels` | 新任务固定 `['overlay']`（或明确兼容策略） |
| `src/host/delivery.ts` | card/delivery 只看 `task.notify.channels` | 按全局 settings 算 effectiveChannels，卡片与 delivery 同源 |
| `src/host/routes.ts` | `/due` 构建卡片、`/settings/update` 校验 patch | `/due` 使用 settings；settings route 接受新字段 |
| `src/client/api.ts` | `SettingsPayload` 无 `desktopNotifications` | 加类型字段 |
| `src/client/settings-modal.ts` | 有 `defaultChannels` system 复选框，没有全局开关/测试按钮 | 改为全局开关、权限状态、测试、平台引导；移除 system 多选 |
| `src/client/task-editor.ts` | 有系统通知复选框、状态、测试按钮 | 移除系统通知 UI 与测试逻辑 |
| `src/client/task-draft.ts` | Draft 有 `channels` | 明确新任务/编辑旧任务策略 |
| `src/client/feature-hints.ts` / dictionaries | 系统通知文案是旧的「每个任务勾选」 | 改为「设置中开启一次，全局生效」 |
| tests | `delivery.test.ts` 旧 system 占位、`routes.test.ts` 旧 defaultChannels | 重写/新增 AC-N 测试 |

**工作量评估**：规划 2.5–4 人日为偏乐观。考虑上述链路、测试重写、设置 UI 权限状态机、任务编辑器移除、文档/打包，建议按 **3–5 人日** 预留，单人 4–5 个工作日；如果只做最小闭环（不改任务编辑器旧测试/权限状态机）可压到 2.5–3，但不建议作为发布门槛。

## 6. 评审结论

**一句话：产品方向正确，但当前 0.7.0 规划与需求 v1.19 有 4 个 P0 口径冲突，且设置/生效/测试链路未冻结；修完本节 R01–R10 后再开工，预计 3–5 人日。**
