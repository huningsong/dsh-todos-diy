## 0 总体结论

**结论：需修改后开工（有条件开工）。**

D-25 的产品方向成立——删除 `dueDate`、`endAt` 作为唯一截止、`phase` 读时派生、四阶段页签 + 循环/暂停独立筛选、取消 `endAt` 自动完成，都是对现有模型问题的正确修复，不需要推翻。当前代码也处于健康基线：host/client/test 三份 `tsc` 均 0 错误，572 个单测全部通过，`verify-pack` 通过。

但「需求已更新」不等于「可直接冻结给实现」：当前 v1.2 仍有 **8 个 P0 级文档缺口**，以及 **8 个必须在批次 1 前拍板的契约点**（见 §9）。这些问题会直接造成验收失败、数据迁移不确定或跨模块返工，不能留到编码时「按理解实现」。

**三句话结论：**

1. **本轮开发范围应只包含 D-25 主模型重构 + 配套测试/文档更新**；自然语言录入（NLP）复核后仍建议放 v1.1，不并入本轮。
2. **文档侧需要先做一轮「一致性修订」**：至少修完 §2 的 8 个 P0，并把 §3 中影响接口/验收口径的 P1 一并冻结；同时更新 README、开发会话提示词、package.json、市场物料这四类「旧模型残留」。
3. **工作量需要重估**：需求 §11 给 D-25 追加 **+3–5 人日**，按实际代码影响（23 个文件、113 处 `dueDate`、28 个测试文件、主文件 + 归档三链路迁移）应为 **8.6–13.0 人日**（3 人并行约 6–8 个工作日）；对外排期不要沿用 3–5。

## 2 P0 必须修改（开工阻断）

以下 8 项会直接造成验收失败、数据迁移不确定、接口契约返工或数据丢失，必须在冻结需求前修掉。其中 R01–R05 对应详细报告的 RC-01～RC-05；R06 为本评审新增的术语冲突项，R07/R08 分别对应详细报告的 RC-07/RC-18（因跨文档与数据安全风险提升为 P0）。

### R01 AC-30 的计数变化自相矛盾

- **问题**：AC-30（`需求-v1.md:1189`）写「一条进行中的任务已过 `endAt`」点完成后「进行中 -1、已超期 -1、已完成 +1（若已超期则先计入超期）」。但按 F4.10（`需求-v1.md:335`），`inProgress = startAt ≤ now < endAt`、`overdue = now > endAt`，同一 `now` 下两者互斥；任务不可能同时属于「进行中」和「已超期」。
- **建议**：拆成两条 AC：
  1. 进行中任务（`now < endAt`）完成 → `inProgress -1 / done +1`，`overdue` 不变；
  2. 已超期任务（`now > endAt`）完成 → `overdue -1 / done +1`，`inProgress` 不变。
  明确两次 `/snapshot` 的 `serverTime` 与比较时刻。
- **影响**：完成动作的徽标迁移无法验收；测试只能按实现解释写，失去判定力。

### R02 迁移规则三处冲突，且不能假设「无历史数据」

- **问题**：
  - AC-41（`需求-v1.md:1200`）写「原 `dueDate` 映射到单次任务 `endAt` 的日期（仅当 `endAt` 缺失时），否则丢弃并记 warning」；
  - F6.8（`需求-v1.md:374`）写「**丢弃 `dueDate`**、保留 `once.startAt` 并补 `startAtSource="explicit"`」；
  - F4.11（`需求-v1.md:336`）写「导入带 `dueDate` 的旧文件经 1→2 迁移丢弃该字段并给出 warning」；
  - `优化-任务时间与状态模型.md:146` 以「v1 未发布，无历史包袱」为由建议直接丢弃，但仓库已有 v0.1.0，README 写「可安装使用」，不能按无历史数据处理。
- **建议**：冻结一条唯一迁移规范：
  1. v1 → v2 一律删除 `dueDate`；
  2. v1 单次任务的 `once.endAt` 本就必填，因此不把 `dueDate` 映射到 `endAt`；若旧数据确实缺 `endAt`，判为非法旧数据，`migration-failed` 并保留原文件（不猜测）；
  3. 补 `once.startAtSource="explicit"`、`notify.endReminder=true`、`state.firedStartAdvance/firedEndAdvance/missedStart/missedEnd/missedCount` 默认值；
  4. `tasks.json`、`archive/completed-*.json`、`archive/index.json`、`POST /import` 四条链路走同一迁移函数；
  5. 给出迁移前/后样本、warning 列表与回滚策略（`tasks.json.bak`）。
- **影响**：旧 v0.1.0 用户升级可能丢截止时间、产生 `endAt <= startAt` 非法任务；AC-41 无法判定通过/失败。

### R03 验收门槛漏掉 AC-28～AC-43

- **问题**：§10.4（`需求-v1.md:1272`）写「手动 E2E：AC-01 至 AC-27 全部通过；AC-28 按 D-02 的拍板结果执行，未拍板前记录为待决策」。但 D-02 已明确拍板「v1 不接入 Agent 会话」；更严重的是 AC-29～AC-43（D-25 的四视图、统计、`endAt` 不自动完成、迁移、`endReminder`）全部不在门槛内，D-25 功能完全未实现也能通过发布门。
- **建议**：改为「AC-01 至 AC-43 全部通过；AC-28 按 D-02 已拍板执行」；若担心 P1 用例过多，可拆「P0 AC 必过 + P1 AC 抽样」，但必须给出 AC-29～AC-43 的归属里程碑与覆盖矩阵。
- **影响**：D-25 的 P0 功能可整体漏测；发布门槛形同虚设。

### R04 单次任务没有任务级时区字段

- **问题**：F2.6（`需求-v1.md:304`）要求「每条任务独立保存 IANA 时区」；但 §7.4 字段表（`:730`）只有 `rule.timeZone`，而 `kind=once` 的 `rule=null`，`once` 示例（`:667-671`）也没有时区字段。于是 F3.2「默认到该日 23:59:59.999（任务时区）」、F8.2「列表行显示任务时区 UTC±HH:MM」、F9.1「新建任务默认继承全局时区」对单次任务均无落点；F9.1 的验收只写 `rule.timeZone`，对 once 不成立。
- **建议**：在数据模型补 `once.timeZone`（当前代码 `OnceWindow` 已有该字段，只是需求漏写），或提升为 Task 顶层 `timeZone`；同步 F2.6/F3.2/F8.2/F9.1/F7.2 schema 与 `TaskView.timeZone/utcOffset`；增加「新建 Asia/Tokyo 的 once 任务，startAt/endAt 均按 Tokyo 解释」的 AC。
- **影响**：单次任务日期时间可能按错误时区解释；列表偏移显示无法实现；F9.1 的 P0 验收对 once 缺失。

### R05 `TaskState` schema 三处不一致，且把只读 `fired` 落盘

- **问题**：F1.3（`需求-v1.md:290`）要求 13 个 state 字段（含 `firedStartAdvance`、`firedEndAdvance`、`missedStart`、`missedEnd`、`missedCount`）；但 §7.4 JSON 示例（`:644-653`）只有 8 个字段，字段表（`:742-744`）只定义 `lastFiredAt/lastOccurrenceKey/fired`，F6.2 持久化清单（`:368`）也未包含新增字段。示例还把 F3.4 明确「不单独持久化」的 `fired` 写进 JSON。
- **建议**：定义唯一的 `TaskState` schema：字段名、类型、默认值、是否持久化、是否派生；从示例删除 `fired`（改为读取时投影）；补齐 F6.2；为 `firedStartAdvance/firedEndAdvance/missedStart/missedEnd/missedCount` 写明触发语义；补一条「导入含 `fired` 的 warning」用例。
- **影响**：重启后 advance/missed 状态丢失；导入导出丢字段；实现方按示例会把派生字段落盘，违反 F3.4/F6.2。

### R06 `phase` 一词三义：任务阶段 / occurrence 节点 / 模板变量

- **问题**：术语表（`需求-v1.md:98、100`）里 `phase` 指 occurrence 的提醒节点（`start`/`end`/`advance`），§7.5 `Occurrence.phase` 也是这个含义（`:770`）；D-25 又把 `phase` 用作任务阶段（`notStarted/inProgress/overdue/done/paused/recurring/archived`，`:725`）；F5.4 的模板变量 `{phase}`（`:357`）则指提醒节点。三个概念同名，API 字段、类型、UI、模板变量会互相污染。
- **建议**：在术语表新增「任务阶段」词条，并二选一改名（推荐）：
  - 任务侧用 `stage`（或 `taskPhase`），occurrence 侧保留 `phase`；或
  - occurrence 侧改 `node`，任务侧保留 `phase`。
  同步 `TaskView.stage`、`Occurrence.phase`、`{phase}` 模板变量说明与全部 AC。
- **影响**：类型签名和 API 字段冻结前若不解决，`TaskView.phase` 与 `Occurrence.phase` 必然混淆；模板 `{phase}` 在任务阶段化后会渲染出错误内容。

### R07 缺口清单 D-22 的结论与需求/评估/README 相反

- **问题**：`待讨论-缺口清单.md:19` 的 D-22 结论仍写「作为「进行中」页签末尾独立分组」；而 `需求-v1.md:335`（F4.10）和 `:416`（F8.11）明确「已暂停 = 独立筛选/折叠区，不混入任何阶段页签」；`评估-任务时间与状态逻辑.md:9` 用户拍板同样如此；`README.md:41` 也已改为「独立筛选不混入阶段页签」。缺口清单是开发会话第一阅读入口，实现方大概率照它做。
- **建议**：立刻把 `待讨论-缺口清单.md:19` 改为「**已暂停 = 独立筛选/折叠区，不混入任何阶段页签；不计入四阶段徽标**」，并重写 D-22 正文的旧三视图措辞。
- **影响**：暂停任务被塞进「进行中」页签，徽标数与行数不一致，直接违反 D-22 拍板。

### R08 彻底删除缺少 `confirm` 参数，存在误删风险

- **问题**：F4.1（`需求-v1.md:326`，P0）要求「彻底删除必须二次确认（API 需 `confirm:true`）」；但 §7.8 的 `POST /tasks/delete`（`:996`）只有 `{id,purge?}`，F7.4 的 `todo_reminder_delete` 也只有 `id,purge?`，均无 `confirm`。按当前契约 `purge=true` 可在无二次确认下执行。
- **建议**：HTTP `/tasks/delete` 与 `todo_reminder_delete` 均增加 `confirm?: boolean`；`purge=true && confirm!==true` 返回 `invalid_argument`；F7.4 错误码补 `invalid_argument`；补 AC「缺 confirm 返回错误、带 confirm 成功」。
- **影响**：彻底删除绕过二次确认，属于不可逆数据丢失风险。

### 6.4 关键实现风险

1. **TaskView round-trip**：`TaskView extends Omit<Task,'state'>`，加 `phase/priority.remainingMinutes/startAtSource` 后，必须拆 `Task` / `TaskView` / `TaskInput`，否则 F1.1 的 round-trip 无法自洽（且现有 `review-fixes.test.ts` 只测 recurring）。
2. **多时区 `today` 耦合**：现有 67 行涉及 `today/todayFor/todayKey/localDateKey`，`taskRoutes.optionsFor`、`toolDefs.view`、`delivery.buildReminderCard`、`archive.quarterOf` 均忽略 `once.timeZone`。D-25 后 phase/priority 应按绝对时刻比较，只保留 `overdueDays` 的任务时区本地日期。
3. **counts 现有 bug**：`repoQuery.queryTasks` 先按 `status/kind` 过滤再算 counts（`repoQuery.ts:58-63`），注释与实现不符；六值后会把「筛选条数变化」放大成「徽标跳变」。
4. **归档迁移绕过 `coerceTask`**：`readQuarter`/`findArchivedTask` 直接返回原始 JSON，v1 的 `dueDate`/缺 `startAtSource` 会进入 v2 系统；必须先迁移 + coerce，再返回。
5. **客户端无分页/无边界刷新**：`panel.load` 只取第一页，`nextCursor` 被忽略；D-25 后 view 更多，必须补 cursor 状态与「加载更多」，并实现 `serverTime` 偏移 + `nextTransitionAt` 定时器 + 60s 兜底。
6. **工作树混入上一轮评审修复**：当前有 69 个未提交文件；建议先提交/归档这批评审修复，再开 D-25 分支，否则最终 diff 无法区分「评审修复」与「D-25 重构」。

### 8.2 D-25 失效点

《评估-自然语言录入.md》写在 D-25 之前，共 **16 条必须重写**（NL-R01～NL-R16）：`TaskDraft.dueDate`/`draftToPayload` 旧字段、返回结构含 `dueDate`、「日期-only→startAt 09:00」错映射、`start+1h` 默认、D-03「必须双提醒」、`NL-08 dueDate`、AC-40～AC-44 与需求 AC-40～AC-43 编号冲突、Prompt/语料中的旧字段等。D-25 后的正确映射：`once.startAt?`（空 = createdAt，无 #start）+ `once.endAt`（唯一截止；日期-only → 23:59:59.999）；`notify.endReminder` 默认 true；不再有 `dueDate`。

### 8.3 版本建议

**维持 v1.1，不纳入本轮 D-25 实现。**

理由：
1. NLP 与 D-25 修改同一批文件（`task-editor.ts`、`validate.ts`、`taskRoutes.ts`、`panel.ts`、测试基线），同轮做会在移动地基上盖房；
2. 修正后工作量 **MVP 8–10 人日、完整质量 11–13 人日**（原估 4–6/7–10 低估 3–5 人日）；
3. NF8「不联网、不上传任何任务数据」与调用模型直接冲突，必须先修改隐私条款并做产品决策；
4. 模型可用性/额度/延迟尚未验证；同轮引入会把「模型不可用」变成 D-25 发布阻塞风险。

若产品坚持提前准备，本轮只建议做 **0.5–1 人日非交付预研**：写 F10 需求草案、spike 验证零依赖构造 messages、在 D-25 的 `TaskDraft` 预留 `startAt?`/`endReminder` 字段；**不写 `/parse` 生产路由、不加输入框**。
